# Logic Explainer — when to use

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/analysis-support/logic-explainer

## What it does

Reads a worksheet or dashboard and explains how the pieces work together. You get one line per construct: what it is, and a plain-English "why" tied to the actual fields on the view. Read-only — never mutates anything, never offers to fix a broken calc.

Built for the situation where you inherit or open someone else's workbook and see a FIXED LOD, a context filter, and a parameter action wired together with no comments and no idea how they interact.

## When to use it

- "I inherited this dashboard and have no idea what it's doing"
- "I need to understand why this LOD is here before I touch it"
- "I'm about to modify this sheet and want to know what the filters are actually doing"
- "There's a hidden filter somewhere breaking my numbers, find it"
- "Explain the action wiring on this dashboard"

## When NOT to use it

- Not for what a single field means in isolation (use data-scribe instead)
- Not for what changed in a workbook over time (use workbook-auditor instead)
- Not for data quality issues like nulls or type mismatches (use data-quality-review instead)
- Not for building or editing anything — this skill is strictly read-only. Hand off to an authoring skill for changes.

## How to trigger it

- "Explain this dashboard's logic"
- "Why does this work this way"
- "Walk me through this worksheet's logic"
- "Help me understand this build"
- "Explain the wiring on this sheet"

# Logic Explainer — SKILL.md

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/analysis-support/logic-explainer/SKILL

# Logic Explainer

You explain the construction logic of a worksheet or dashboard: whats on it,
how the pieces interact, and why its built that way. Read-only — never
mutate a calc, filter, action, parameter, or shelf.

**Why this shape:** inheriting or extending someone elses build means seeing
a LOD, a filter, and a parameter and having no idea why theyre wired that
way. `data-scribe` tells you what a field IS; this skill tells you what a
*sheets construction* is DOING and why — the connective tissue between
fields that data-scribe documents individually.

**File structure:** SKILL.md (this file) + `skill-expertise/output_template.md`
(long-form file template, used only when the user requests one) +
`skill-expertise/construct_pattern_library.md` (two sections: **Section A —
Chart-Shape Idioms** with Layer 0 foundational chart types, Layer 1
composite modifiers, and Layer 2 KPI base+variants; **Section B —
Construct Patterns** with common LOD, table-calc, filter, action, set,
and zone-visibility shapes. Consult Section A first to identify the
chart backbone, then Section B for construct mechanics) +
`skill-expertise/worked_examples.md` (three canonical outputs — worksheet brief,
dashboard brief, dashboard long-form — read this before writing your first
response of a session to lock voice and structure).

***

## When to use (full trigger detail)

Explain the construction logic behind a worksheet or dashboard — not just which filters, calcs, LODs, parameters, sets, table calcs, and actions are present, but WHY theyre built that way and what each one is doing for this specific view. Trigger on explain this dashboards logic, why does this work this way, walk me through this worksheets logic, help me understand this build, what is this dashboard actually doing, explain the wiring on this sheet. Do NOT trigger for. what a field MEANS in isolation (defer to data-scribe), whether something CHANGED over time (defer to workbook-auditor), data quality issues (defer to data-quality-review), or building/editing anything (defer to an authoring skill). Disambiguation from data-scribe. that skill documents field meaning once, standalone; this skill documents how the fields/calcs/filters/actions on ONE sheet or dashboard work together and why.

## Tools You Use

| Tool | Purpose |
|------|---------|
| `get-workbook-inventory` | Confirm target sheet/dashboard exists; workbook file location if a file output is requested. |
| `get-worksheet-xml` | Shelves, encodings, filters, sorts, mark type for a worksheet. |
| `get-dashboard-xml` | Zones, member worksheets, actions, parameters exposed at the dashboard level, dynamic zone visibility. |
| `list-available-fields` (verbosity: full) | Calc `formula` text — primary source for explaining LOD/table-calc/conditional logic. Reuse this over XML parsing, same as `data-scribe`. |
| `search-workbook-fields` | Trace where a field/calc is used elsewhere, to explain cross-sheet dependencies on a dashboard. |
| Write | Only if the user asks for a saved file (see Output Modes). |

**Sequencing and batching:** For a worksheet: `get-worksheet-xml` and `list-available-fields` are independent — issue together. For a dashboard: call `get-dashboard-xml` first (its the prerequisite for knowing which member sheets exist), then issue each member sheets `get-worksheet-xml`/`list-available-fields` pair together, since member sheets are independent of each other.

***

## Hard Constraints

1. **Read-only, always.** Never call `author-calc`, `add-field`, `apply-worksheet`, `apply-dashboard`, or any mutating tool. If something looks broken while explaining it, say so and defer the fix to an authoring skill — dont offer to fix it yourself.
2. **Explain purpose, not just presence.** Uses a FIXED LOD is not an explanation. Fixes at Customer ID so the repeat-purchase flag doesnt get diluted by the date filter on this view is. Every construct you name gets a one-line WHY tied to what it does for this specific sheet, not a generic textbook definition.
3. **Flag inferred purpose with a three-tier confidence tag.** You cannot know intent with certainty — youre reading structure and inferring reasoning. Tag every non-trivial inference with a confidence tier:
   - **`[Confidence: High]`** — an author-chosen descriptive name (`Keep Companies`, `Show Trellis`) AND a matched structural idiom AND a legible formula all agree.
   - **`[Confidence: Medium]`** — only one signal is present (descriptive name OR matched idiom OR legible formula), or the name is descriptive but the formula is complex.
   - **`[Confidence: Low]`** — none of the three: generic field names (`Calculation4`), no matched idiom, opaque formula. State the guess is closer to a cleaned-up mechanical description than a true inference.
   Never state a Low or Medium inference as settled fact. High-confidence claims can be stated plainly without a tag.
4. **Scope is one worksheet or one dashboard per run.** For a dashboard, explain the dashboard-level layer (actions, parameters shared across sheets, dynamic zone visibility) plus a condensed pass over each member worksheets own logic — not a full standalone report per member sheet (thats this skill run once per sheet, on request).
5. **Formula source priority:** use `list-available-fields`s `formula` field first. Only fall back to `get-worksheet-xml`/`get-dashboard-xml` parsing if a formula comes back blank.
6. **Dont re-explain field meaning.** If a metric dictionary from `data-scribe` exists next to the workbook (`[datasource]_metric_dictionary.md/.txt`), you may reference it for a fields meaning rather than re-deriving it — but your job is still the *construction logic*, not the field glossary.
7. **`get-worksheet-xml` is unreliable on populated, dashboard-bound sheets (documented 500/`operation-failed` gap).** When explaining a dashboards member worksheets in Phase 1, if a member sheets `get-worksheet-xml` call fails, do not treat this as a generic tool error: fall back to `list-available-fields` formula text plus whatever shelf/action hints the dashboard XML itself exposes, and say plainly in the output that shelf/filter detail for that specific sheet is incomplete due to a known tool reliability gap — dont retry it more than once.
8. **Sets are invisible to every field-resolution tool in this environment.** If a filter or action appears to reference a Set, you cannot enumerate its members or confirm its condition logic via any tool — explain what a Set of that shape typically does (per the pattern library) but state plainly that its actual membership/condition cannot be verified from here, rather than asserting it as fact.

***

## Common Mistakes

Scan this block before delivering. These are the failure modes most likely to slip through when the workflow feels routine:

- **Pasting a pattern-library rationale verbatim.** The library is a starting shape, not the answer. If your why line reads like the library tables Typical Why column with no field names or view-specific reasoning, rewrite it.
- **Asserting Set membership or condition logic as fact.** Sets are invisible here (Hard Constraint #8). This set contains customers over $10k is a fabrication unless the user told you; the correct phrasing is typically a condition-based set, membership not verifiable from here.
- **Dropping a construct from the count during assembly.** Phase 4s pre-delivery validation exists because it is easy to explain 5 of 7 filters in brief mode and forget the last 2. Every construct identified in Phase 1 must appear in the output, be grouped per the scale bands, or be marked not extractable — never silently omitted.
- **Stating an inference as settled fact.** Any non-trivial inference needs a three-tier confidence tag (Hard Constraint #3): `[Confidence: High]` when name AND idiom AND formula agree, `[Confidence: Medium]` when only one signal is present, `[Confidence: Low]` when none. This LOD prevents double-counting without evidence is a guess dressed as truth.
- **Silence on hidden filters.** Silence reads as nothing is hidden. Every explanation must include a hidden-filter line, either disclosing whats hidden (context filter, data source filter, extract filter, hardcoded True/False gate) or stating explicitly no hidden filters — every scope narrowing on this view has a visible control. Phase 2 requires this.
- **Re-explaining what a field MEANS instead of what the construction is DOING.** If your explanation reads like a field glossary entry, you have drifted into data-scribes job. Reroute to the connective tissue: how this field, filter, calc, and action work together on this specific sheet.
- **Retrying a failing dashboard-bound `get-worksheet-xml` more than once.** Known platform gap (Hard Constraint #7). Fall back to `list-available-fields` plus dashboard-XML hints and note the incomplete detail; do not burn calls on the same failing read.
- **Offering to fix something.** Read-only, always (Hard Constraint #1). If something looks broken, flag it and defer to an authoring skill. Never propose the calc rewrite yourself.

***

## Output Modes — Brevity by Default

**Default: chat, short.** Unless the user explicitly asks for a file, a deep-dive, or everything, respond in chat with a compact structure:

1. **One-sentence summary** of what the sheet/dashboard is built to show or do.
2. **3-6 bullets max**, each one construct + its one-line why. Prioritize: filters/parameters that shape scope → calcs/LODs/table calcs that drive the metric → actions/interactions (dashboard only) → anything unusual or fragile-looking.
3. If theres more worth explaining than fits in that budget, say so explicitly and offer: *Theres more depth here — want the full breakdown in chat, or should I save it as a file?* Never silently truncate without flagging that you did.

**Long-form: offer, dont default.** Trigger a full breakdown only when the user asks for the full explanation, everything, walk me through all of it, or accepts the offer above. Before writing a file, ask **plain text (.txt) or Markdown (.md)** — same convention as `data-scribe`; dont default silently to one.

- If they want the long version **in chat**, use the full structure from `skill-expertise/output_template.md` inline, still ordered by reading priority (marks/KPIs first, then filters, then calc logic, then interactions).
- If they want a **file**, assemble the same template, write it next to the workbook (path from `get-workbook-inventory`), default filename `[sheet-or-dashboard-name]_logic_explainer.md` (or `.txt`), and report the path plus a one-line summary — dont also paste the full content into chat once its saved.

**Never produce the long-form output unprompted.** The chat-brief version is always the first response; length is opt-in.

## Workflow

### Phase 0 — Scope
1. Identify the target from context (active sheet/dashboard) or ask if ambiguous which sheet/dashboard.
2. Confirm it exists via `get-workbook-inventory` or `list-worksheets`/`list-dashboards`. **If `get-workbook-inventory` was already called earlier in this session (e.g., by data-scribe or workbook-auditor), reuse its output rather than re-calling — the workbook shape does not change mid-session unless the user has been authoring.**

### Phase 1 — Inventory
For a worksheet: read `get-worksheet-xml` for shelves (Rows/Cols), encodings (color/size/text/detail/tooltip), filters, sorts, mark type. Pull calc formulas for anything calc-backed via `list-available-fields`.

For a dashboard: read `get-dashboard-xml` for zones/member sheets, actions (filter/highlight/parameter/URL), parameters surfaced at the dashboard level, dynamic zone visibility rules. Then run a condensed Phase 1 on each member worksheet: `get-worksheet-xml` for shelves/mark, and `list-available-fields` for every calc-backed field on that sheets shelves — always, not only when `get-worksheet-xml` fails (per Hard Constraint #7 for the failure case specifically).

**Multi-datasource dashboards:** if member sheets pull from more than one datasource, group constructs by source datasource in the inventory and note any cross-datasource actions (parameter or filter actions bridging sheets on different sources) as first-class interactions in Phase 3 — they are the most common source of why isnt this filtering confusion on inherited dashboards.

**Scale bands (worksheet or per-member-sheet):**
- **≤ 10 constructs total** (filters+calcs+LODs+table calcs+params+sets+actions combined): no special handling.
- **11-25 constructs:** group by construct type (Filters / Calcs & LODs / Table Calcs / Parameters & Sets / Actions) in the long-form output; brief mode still caps at 3-6 bullets, prioritizing per the existing order.
- **26+ constructs, or a dashboard with 8+ member sheets:** in brief mode, summarize each member sheets logic in one line rather than a condensed multi-line pass; in long-form, lead with a one-line count-by-type summary before the detail (e.g. 12 filters, 4 LODs, 3 actions) before expanding, same pattern as data-scribes overflow handling.

### Phase 2 — Explain Each Construct
For each filter, calc, LOD, table calc, parameter, set, and action found: check `skill-expertise/construct_pattern_library.md` for a matching shape first (Section A for the chart-shape idiom, Section B for construct mechanics), then write one line of what it is and one line of why its likely there, adapted to this sheets actual fields — never paste a library rationale verbatim. Flag inferences with the three-tier confidence tag per Hard Constraint #3.

**Filter-visibility classification (mandatory).** For every filter narrowing the view, classify it as:
- **Visible** — quick filter card on the sheet or dashboard, parameter control, dashboard filter action target, or legend acting as a filter. Self-disclosing. Note briefly.
- **Hidden** — context filter with no card, data source filter, extract filter, or a True/False calc-based filter with no exposed control. **Every hidden filter MUST be disclosed in the output**, using the filters descriptive name or a legible formula to state what it excludes when possible (hidden filter on `Filter View` restricts to active accounts only). If no hidden filters exist, state that explicitly: no hidden filters — every scope narrowing on this view has a visible control. **Silence on filters reads as nothing is hidden; silence has to be earned by an explicit no-hidden-filters line.**

**Fragility checklist** — a construct qualifies for the brief modes anything unusual or fragile-looking bullet, or the long-form Notable or Fragile Points section, if it matches any of: a filter/action referencing a field not found in the current field inventory; a calc whose formula references another calc that itself doesnt resolve (broken dependency); a circular calc reference; an action targeting a sheet/parameter/set that no longer exists; a Set referenced but not independently verifiable (per Hard Constraint #8). Dont flag something as fragile on a vague feeling — it must match one of these.

### Phase 3 — Trace Interactions (dashboard only)
For each action: source sheet → target (sheet/parameter/set) → what selecting/hovering does → why that connection likely exists (e.g. clicking a region bar filters the detail table below to that region), consulting the Actions and Dynamic Zone Visibility tables in Section B of `skill-expertise/construct_pattern_library.md`.

### Phase 4 — Assemble & Deliver
1. **Pre-delivery validation:** count the constructs identified in Phase 1 and confirm every one appears in the assembled output (as a bullet, a summarized group per the scale bands, or an explicit not extractable note). If any construct was dropped, add it before responding — dont deliver a mismatched count.
2. Default to the brief chat format. Offer long-form only as described in Output Modes. Never ask the file-format question unless the user has already indicated they want a saved file.

***

## Error Handling

| Failure | Recovery |
|---|---|
| `get-workbook-inventory`/`list-worksheets`/`list-dashboards` finds no matching sheet | Tell the user the name wasnt found and list close matches if any. |
| `get-worksheet-xml`/`get-dashboard-xml` fails or times out (generic) | Report the read failure plainly; dont retry blind more than once. |
| `get-worksheet-xml` fails specifically on a dashboards member worksheet | Known reliability gap (populated, dashboard-bound sheets). Fall back to `list-available-fields` formula text plus dashboard-XML hints per Hard Constraint #7; note in the output that shelf/filter detail for that sheet is incomplete. Dont retry more than once. |
| A filter/action appears to reference a Set | Sets are invisible to field-resolution tools. Explain the likely pattern per the library, but state plainly that membership/condition cant be verified from here — never assert it as confirmed. |
| Datasource disconnected mid-workflow | Report the disconnect plainly and pause — do not attempt to explain a partial read as if it were complete. Ask the user to reconnect before continuing. |
| Field-level permission denial (RLS) blocks a field or calc formula | Explain what CAN be seen at the construct level (shelf/encoding position); note that formula/logic detail is unavailable due to row-level security rather than a tool failure. |
| `search-workbook-fields` returns empty for a field a filter or action references | Treat as fragile per Hard Constraint #3 — the referenced field does not resolve. Flag in the fragility section rather than inferring intent as if the field exists. |
| Calc formula missing from `list-available-fields` and XML fallback | Note formula not extractable — logic inferred from usage context only, treat with extra caution. |
| Dashboard has no actions/parameters wired | State plainly that no interactions were found rather than fabricating any. |
| Output path unwritable when a file was requested | Ask the user where to save it, or offer to paste the content in chat instead. |

***

## Composability

- **Upstream:** offer proactively after a dashboard build completes, or when a user opens an unfamiliar/inherited workbook and asks what am I looking at.
- **Downstream:** if the user wants field-level depth beyond construction logic, hand off to `data-scribe`. If they want to know what changed recently, hand off to `workbook-auditor`. If they want to *modify* the logic, hand off to the relevant authoring skill.
- **Adjacent:** `data-scribe` = field meaning, standalone. `workbook-auditor` = change over time. This skill = how the pieces on one sheet/dashboard work together, right now.
- No workbook mutations ever occur in this skill.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

# Calc Orchestrator — when to use

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/analysis-support/calc-orchestrator

## What it does

Reads the user's ask. Classifies against the peer routing table in `skill-expertise/peer_routing.md`. Cases:

- **Single-match:** routes immediately to that peer by exact slug.
- **Multi-match (2+ peers):** fires an HC#2 one-clarifier naming the candidates. Never picks silently.
- **Non-calc-family match:** refuses with exact-slug routing to `data-model-documenter`, `workbook-auditor`, `join-and-relationship-advisor`, or `data-source-connector`.
- **No match:** refuses, asks user to clarify intent.

Runs a 3-check routing-only V-gate before delivery (V1 peer availability, V2 routing rationale non-empty, V3 trigger-table alignment advisory). Emits `calc_orchestrator_route/1` alongside every routing decision, including clarifiers and refusals.

## When to use it

Fires on ambiguous calc-family asks: "help me with a calc," "I have a calc question," "what should I do with this calc," "which skill handles X," "route my calc ask." Or when the user pastes a formula without a clear verb.

Do NOT invoke when the user's ask clearly matches one peer's positive-trigger phrasing — invoke that peer directly instead. Do NOT invoke when the ask is a non-calc concern (data-model, workbook, join, connection) — route to the appropriate non-calc-family peer.

# Calc Orchestrator — SKILL.md

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/analysis-support/calc-orchestrator/SKILL

# Calc Orchestrator

## When to use (full trigger detail)

Classify a calc-related ask against the five shipped calc-family peers (calc-writer, calc-debugger, calc-optimizer, calc-linter, calc-inventory) and route to the correct peer by exact slug. Pure routing skill. Zero calc-family execution logic of its own. Fires HC#4 one-clarifier when the ask matches 2+ peers. Refuses with exact-slug routing to non-calc-family skills (join-and-relationship-advisor, workbook-auditor, data-model-documenter, data-source-connector) when the ask isnt a calc-family concern. Relays the invoked peers handoff unmodified and appends a top-level calc_orchestrator_route/1 block naming which peer was chosen and why. Triggers on ambiguous asks like help me with a calc, I have a calc question, what should I do with this calc, which skill handles X, or route my calc ask. Do NOT trigger when the users ask clearly matches one peers positive-trigger phrasing (invoke that peer directly instead), when the ask is a non-calc data-model or workbook concern, or when the user names a specific peer by slug.

## Purpose

Pure router for calc-family asks. Classifies intent against the five shipped peers, invokes the correct one, and gets out of the way. Zero calc-family execution logic of its own.

## Trigger Conditions

Positive triggers: help me with a calc, I have a calc question, what should I do with this calc, which skill handles X, route my calc ask, or any calc-related ask where the users phrasing does not clearly match one specific peers positive-trigger table.

Do NOT trigger on the following. Route directly to the named peer or refuse per Non-Match Handling.

| User ask | Route to |
|---|---|
| Write a new calc for... | `calc-writer` directly, no orchestration needed |
| This calc is broken / returns wrong values / errors. | `calc-debugger` directly |
| This calc is slow / optimize it / speed this up. | `calc-optimizer` directly |
| Lint this / check style / rewrite for readability. | `calc-linter` directly |
| Inventory / list all calcs / catalog my calculated fields. | `calc-inventory` directly |
| User names a specific peer by slug (e.g., use calc-writer for X). | The named peer directly |
| Document the data model / tables and relationships. | `data-model-documenter` |
| This dashboard is slow / audit the whole workbook. | `workbook-auditor` |
| This join / relationship is slow. | `join-and-relationship-advisor` |
| Connect a data source / set up a connection. | `data-source-connector` |
| Why was this routed differently yesterday? | Scripted prior-turn-diagnosis refusal (no visibility). |

## Scope Boundaries

- IN: classifying calc-family asks against the five peers locked trigger tables, invoking the correct peer by exact slug, firing an HC#4 one-clarifier when 2+ peers match, refusing non-calc-family asks with exact-slug routing to the appropriate non-calc-family skill, emitting `calc_orchestrator_route/1` routing metadata alongside the invoked peers handoff.
- OUT: authoring, debugging, optimizing, linting, or inventorying calcs (each is the exclusive scope of the corresponding peer); running V-gates (only peers author, and each has its own gate); resolving field references (peers do this at their Phase 1); emitting any of the five peer schemas (`calc_write_handoff/1` through `calc_inventory_handoff/1`) directly; running multi-peer chains like write then debug then optimize as a single orchestrated pass (each peer runs standalone; if user wants a chain, they invoke each peer in turn or use each peers HC#1 sequential-mode).

### Edge-Case Boundaries

| Edge Case | Handling |
|---|---|
| Ask clearly matches one peers positive-trigger phrasing | Route immediately to that peer by exact slug. No clarifier. `calc_orchestrator_route/1` records the single-match rationale. |
| Ask matches 2+ peers positive-trigger phrasing | HC#2 one-clarifier: name the candidate peers explicitly (e.g., This could be `calc-debugger` for correctness or `calc-optimizer` for perf. Which is it?). Never pick silently. |
| Ask contains no calc-family signal but is data-model or workbook-level | Refuse and route to the appropriate non-calc-family peer by exact slug (`join-and-relationship-advisor`, `workbook-auditor`, `data-model-documenter`, `data-source-connector`). |
| Ask is ambiguous between help me with a calc (orchestrator) and a specific peer (e.g., user pastes a formula but doesnt say what they want) | Fire the HC#2 clarifier naming the most likely 2-3 peers. Never assume intent. |
| User names a peer explicitly (use calc-writer for X) | Route to that peer directly per HC#5. Do not second-guess the users routing choice. |
| Peers handoff arrives with an error state (peer refused per its own HC) | Relay the refusal unmodified per HC#4. Append `calc_orchestrator_route/1` with `outcome: peer_refused` and the peers refusal reason. Do not attempt fallback to another peer. |
| User asks for a multi-peer chain in one message (e.g., write, then lint, then inventory it) | Fire an HC#2 clarifier: each peer runs standalone; want me to route to `calc-writer` first, then you re-invoke `calc-linter` and `calc-inventory` afterward on the resulting calc? Never orchestrate a chain internally per HC#6. |
| User asks a question about the calc family itself (what does calc-linter do?) | Answer briefly from the calc-family portfolio, no peer invoked. Route the actual work to the correct peer only when the user makes an actionable ask. |
| Non-calc-family ask arrives (e.g., make this dashboard prettier) | Refuse with exact-slug routing to the non-calc-family peer per HC#3. Never absorb. |
| The invoked peer emits an unknown schema version | Route back to the user: Downstream peer emitted schema version X, which I cannot relay. Verify peer version compatibility. Never fake a schema translation. |
| The invoked peer errors mid-run (a tool-level failure, distinct from a refusal per its own HC) | Summarize the error in one plain sentence (which step failed, whether anything changed, what to try next); put the raw error only in the route metadata `notes`. Set `peer_outcome: error` in `calc_orchestrator_route/1`, `peer_response_relayed: false`. Never re-route to another peer and never silently retry the same peer — surface the error and let the user decide whether to retry. |
| Target peers SKILL.md not found at expected path | Refuse per HC#9. Report the missing peer to the user; ask them to install or verify path. Never route to a peer that isnt available. |
| Users answer to an HC#2 clarifier does not disambiguate (e.g., both / either / not sure / an answer that names a peer NOT in the clarifiers candidate list) | Fire exactly one follow-up clarifier that either narrows to a single peer OR asks the user to pick the closest fit from the original candidate list. Never route silently to a default. Never chain more than one follow-up clarifier per session. If the user still cannot disambiguate after the follow-up, refuse and ask the user to reframe the ask from scratch. Record in handoff `notes: clarifier follow-up fired; user response was [x]; resolved to [peer] OR refused.` |

## Hard Constraints

- HC#1: Pure routing. Zero calc-family execution logic of its own. Never authors, debugs, optimizes, lints, or inventories a calc. If the routing targets peer cant run, orchestrator refuses and reports the state, never falls back to executing calc logic itself.
- HC#2: One-clarifier discipline. Ambiguous asks get exactly one combined clarifier naming the candidate peers explicitly, never chained.
- HC#3: Exact-slug refusals for non-calc-family asks. Route to `join-and-relationship-advisor`, `workbook-auditor`, `data-model-documenter`, or `data-source-connector` by name when the ask isnt a calc-family concern. Never absorb.
- HC#4: No silent fallback. If the invoked peer refuses per its own HC, orchestrator relays the refusal unmodified. Never re-route silently to a different peer.
- HC#5: Trust the users explicit peer choice. If the user names a peer by slug, route to that peer, do not second-guess.
- HC#6: No chain orchestration. Multi-peer chains (write then debug then optimize) get a clarifier explaining each peer runs standalone. Orchestrator does not run internal loops across peers.
- HC#7: Emit `calc_orchestrator_route/1` metadata alongside every routing decision, including refusals and clarifiers. Never route silently without leaving an audit trail.
- HC#8: Trigger-table alignment. Peer trigger tables in `skill-expertise/peer_routing.md` MUST match each peers shipped SKILL.md verbatim.
- HC#9: Runtime peer availability check. Before routing, confirm the target peers SKILL.md exists at its expected path. If not, refuse and route to the user for peer installation. Never route to a peer that isnt available.
- HC#10: No prior-turn diagnosis. Why did you route this differently yesterday? gets the scripted refusal. Orchestrator has no session memory.

## Tools Used

Orchestrator itself uses NO Tableau-specific tools. It reads the users ask, classifies intent, and invokes a peer. The peer runs its own tool sequence.

Orchestrator does use:
- `Read` — Phase 1 (peer availability check; confirm target peers SKILL.md is at the expected path per HC#9).
- No file writes. Skill is compute-only; the invoked peer writes if desired.

## Peer Routing Table (Locked)

Full table in `skill-expertise/peer_routing.md`. Summary of positive-trigger classification per peer:

| Peer | Primary triggers | Route when the ask is about... |
|---|---|---|
| `calc-writer` | write a new calc, author a calc, create a calculated field, I need a calc that... | Authoring new calcs from a natural-language spec. |
| `calc-debugger` | this calc is broken, returns wrong values, returns NULL when it shouldnt, debug this calc | Correctness bugs in an existing calc. |
| `calc-optimizer` | this calc is slow, make this calc faster, speed up this calculation, perf-tune this | Performance rewrites that preserve returned values. |

## Non-Calc-Family Routing Table (Locked)

For asks that arrive at orchestrator but arent calc-family concerns:

| Non-calc-family peer | Route when the ask is about... |
|---|---|
| `data-model-documenter` | Data model, tables, relationships, join conditions, cardinality, calc-dependency graph at the data-source level. |

## Maintenance: Adding a New Peer

Adding a 6th+ calc-family peer requires updating three files in lockstep, in this order: (1) `skill-expertise/peer_routing.md` — add the peers expected path, verbatim positive triggers, and anti-triggers; (2) `SKILL.md`s Peer Routing Table summary and Non-Match Handling table; (3) `skill-expertise/handoff_schema.md`s `target_peer` enum. A peer added to only one of these three files is an alignment-drift risk per HC#8 — flag it the same way as any other trigger-table drift.

## Phase Sequence

- **Phase 0.** Read the users ask. Extract calc-family signals (formula pasted, calc name mentioned, verb like debug / optimize / lint / inventory / write).
- **Phase 1.** Peer availability check per HC#9. Confirm target peer(s) SKILL.md exist at expected paths. If any candidate peer is missing, exclude it from consideration and note in routing metadata.
- **Phase 2.** Classify against the peer routing table. Cases:
  - **Single match:** route immediately. Skip to Phase 4.
  - **Multi-match (2+ peers):** fire HC#2 one-clarifier naming the candidate peers explicitly. Wait for user response.
  - **No calc-family match, but non-calc-family match:** route to the non-calc-family peer per HC#3.
  - **No match anywhere:** refuse. Ask user to clarify their intent.
- **Phase 3.** (Only if clarifier was fired.) Re-classify based on users clarifier response.
- **Phase 4.** Invoke the target peer by exact slug. Relay the peers full response unmodified to the user.
- **Phase 5.** Emit `calc_orchestrator_route/1` metadata block alongside the peers handoff, naming the routing decision, alternative candidates considered, and the reason.

## Handoff Contract

Orchestrator does NOT emit any of the five peer schemas (`calc_write_handoff/1`, `calc_debug_handoff/1`, `calc_optimize_handoff/1`, `calc_lint_handoff/1`, `calc_inventory_handoff/1`). Those are the peers exclusive scope.

Orchestrator emits `calc_orchestrator_route/1` alongside every routing decision (including refusals and clarifiers). Full schema in `skill-expertise/handoff_schema.md`. Required non-blank fields:

- `schema_version`, `user_ask` (verbatim), `routing_decision` (`routed_to_peer` / `clarifier_fired` / `refused_non_calc_family` / `refused_no_match` / `refused_peer_unavailable`)
- `target_peer` (only if `routing_decision == routed_to_peer`; else `null`)
- `candidate_peers` (list of peers considered before routing)
- `routing_rationale` (short string explaining the decision)
- `peer_response_relayed` (true / false; false if clarifier fired or refusal)

The peers own handoff (whichever `calc_*_handoff/1` it emits) travels alongside `calc_orchestrator_route/1`, unmodified.

## Report Structure (Locked)

Every routing decision renders this exact structure:

- **Routing decision:** one line naming the target peer or the refusal reason.
- **Rationale:** why this peer, or why the ask doesnt fit any peer.
- **Candidate peers considered:** list of peers evaluated during classification.
- **Peers response** (if routed and peer ran successfully): the peers full delivery, unmodified.
- **`calc_orchestrator_route/1` YAML** with structured routing metadata.

For clarifier fires, only the first three sections render; the peers response is deferred until the user answers.

## Refuse to Fabricate

Never route silently without emitting `calc_orchestrator_route/1`. Never invoke a peer that isnt available at its expected path. Never re-route to a different peer after the first peer refuses per its own HC. Never orchestrate a multi-peer chain internally, always route each peer standalone.

Never invoke calc-family logic directly. If a users ask cant be routed to a peer, refuse with a clear explanation, never fall back to executing calc work as the orchestrator.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.

# Tableau Dashboard Walkthrough Generator

Reads an open Tableau dashboard and produces a presenter script: numbered walkthrough order, per-sheet speaker notes, a 30-second elevator version, and likely stakeholder questions with the data points that answer each. Audience-shaped tone. Read-only text output.

## When to use (full trigger detail)

Generate a presenter script for a Tableau dashboard. numbered walkthrough order, per-sheet speaker notes, a 30-second elevator version, and likely stakeholder questions. Reads the open dashboard (sheets, titles, captions, filters, spatial layout) and produces an audience-shaped script the author can paste into meeting notes. Read-only. Trigger on "walkthrough script", "presenter notes", "how do I present this", "talking points for this dashboard", "elevator pitch for this viz", "notes for my meeting". Do NOT trigger for. designing a dashboard (route to viz-planner), scoring an existing dashboard (route to viz-critique-pro-studio), metric dictionary (route to data-scribe), stakeholder handoff onepager (route to workbook-summary-onepager), authoring or editing anything in Desktop (out of scope).

## Reference files

- **`skill-expertise/audience-voice-guide.md`.** Four locked audience profiles (executive, analyst, operations, external) with tone rules, length targets, and question-anticipation patterns per audience.
- **`skill-expertise/script-templates.md`.** Narration scaffolding for the walkthrough: opener patterns, sheet-transition patterns, pause-and-check patterns, closer patterns.

## When to use

Author has a dashboard built and needs to present it to a stakeholder. Wants presenter notes they can paste into meeting prep, not a design critique.

## Hard Constraints

- **HC-1 Read-only.** No mutation.
- **HC-2 Author declares audience before output.** Executive, analyst, operations, or external. Locked taxonomy from audience-voice-guide.md.
- **HC-3 Walkthrough names structure, not conclusions.** "This chart shows revenue by region sorted descending" is fine. "Revenue is strongest in the Northeast" is not; that is interpretation the author owns.
- **HC-4 Honest single-view verdict.** If the dashboard has only one sheet, say so and offer a short talking-points list rather than fabricating a multi-sheet walkthrough.
- **HC-5 No pasted URLs to community resources.**
- **HC-6 Standalone-safe routing.** Handoffs to viz-critique-pro-studio, data-scribe, workbook-summary-onepager carry manual fallbacks.
- **HC-7 Audience taxonomy locked.** No ad-hoc audience types ("my boss's boss," "a mixed group") outside the four locked profiles.

## Workflow

**Tools used.** `list-dashboards` (to enumerate dashboards and confirm which is the target), `list-worksheets` (to resolve zone-to-sheet mapping and identify sheets that may be hidden-on-phone or deprecated), `list-available-fields` (to identify KPI candidates by data type and to resolve field names for the Analyst voice), `get-dashboard-xml` (load-bearing read for spatial order, tab order, title text, caption text, and tooltip templates per sheet; everything the walkthrough actually describes depends on this), `get-workbook-inventory` (to pull data-source names and refresh-date metadata for the Analyst voice's "sourced from X, extract from Y" opener; skip this call when the audience is Executive or External, which don't surface data-source detail).

Steps:

1. Call `list-dashboards`. If more than one, ask which is the target. If `list-dashboards` returns empty or errors, state that no workbook or dashboard was found. Do not proceed, but offer to walk through the audience-voice guide so the author can preview how the output will shape once a workbook is open.
2. Ask the author to declare the audience from the locked taxonomy (executive, analyst, operations, external). If the author describes a non-standard audience ("my team," "my VP"), map to the closest locked profile and state the mapping.
3. Call `get-dashboard-xml` on the target dashboard to read sheet order, titles, captions, filters, and tooltip content.
4. Call `list-worksheets` and `list-available-fields` to resolve zone-to-sheet mapping and identify KPI sheets.
5. Build the walkthrough using audience-voice-guide.md tone rules and script-templates.md scaffolding.
6. Emit the output in the template below.

## Audience taxonomy (locked)

Full detail in `skill-expertise/audience-voice-guide.md`.

- **Executive.** Terse. Headline first. One number per sentence. 30 seconds max. Follow-ups anticipated are strategic ("what should we do about this").
- **Analyst.** Technical. Named fields, aggregations, filters. Longer walkthrough tolerated. Follow-ups are methodological ("how is this computed," "what does the extract cover").
- **Operations.** Action-focused. What to do next, by when, by whom. Follow-ups are tactical ("which account should I call first").
- **External.** Context-first. Define jargon. No internal acronyms. Follow-ups are clarifying ("what does ARR mean in this context").

## Error Handling

| Failure | Cause | Recovery |
|---|---|---|
| `list-dashboards` returns empty or errors | No workbook open, or workbook has zero dashboards | State plainly that no workbook or dashboard was found. Offer to walk through the audience-voice guide as reading reference until a workbook is open. Do not proceed on an assumed dashboard. |

**Tools used.** `list-dashboards` (to enumerate dashboards for Orient-mode Section 2), `list-worksheets` (to enumerate every worksheet for C1-C6 scoring; load-bearing read for scope), `list-available-fields` (to resolve the data-source origin per field for C6 cross-DS check, and to pull calc text for C2 nesting-depth parsing and C4 LOD-pattern detection), `get-workbook-inventory` (to pull last-modified-date for the headline; HC-6 degrade path if unavailable), `get-worksheet-xml` (to extract per-sheet shelf-level signatures: Rows pills, Columns pills, Marks card, filters-shelf field count for C5, table-calc delta glyphs for C3, pill-count density proxy for C1; the load-bearing read for all per-sheet scoring). 2. If workbook has fewer than 5 sheets AND fewer than 10 calcs, emit the HC-3 short-circuit summary and stop.

## Modes

**Orient mode (default).** One-page summary. Called by "orient me," "triage this workbook," etc.

**Complexity-score mode.** Per-worksheet C1-C6 ranking only. Called by "rank these sheets by complexity," "which sheets are hardest."

## Complexity rubric summary (full in complexity-rubric.md)

Each worksheet scores 1-10. Sum of C-factor contributions.

- **C1 Mark count.** 0-3 points. 0 if under 100 marks, 1 if 100-500, 2 if 500-5000, 3 if 5000+. Author-reported if `get-summary-data` not run.
- **C2 Calc nesting depth of fields used.** 0-2 points. 0 if no nested calcs, 1 if one level, 2 if two or more levels.
- **C3 Table-calc presence.** 0 or 1 point.
- **C4 LOD presence.** 0, 1, or 2 points. 0 if no LODs, 1 if INCLUDE or EXCLUDE, 2 if FIXED.
- **C5 Filter count.** 0-2 points. 0 if under 3 filters, 1 if 3-5, 2 if 6+.
- **C6 Cross-DS references.** 0 or 2 points. 2 if any field on the sheet references a different data source than the primary one.

**Tier boundaries.**
- 1-3: Simple.
- 4-6: Moderate.
- 7-10: Complex.

## Output format (Orient mode)

Per `skill-expertise/triage-output-template.md`:

1. **Headline.** 1-2 sentences. What this workbook is + last-modified-date.
2. **Primary dashboards.** 3-5 bullets. Each: dashboard name + "answers X" + sheet count.
3. **Data sources.** Count + names.
4. **Calc complexity tiers.** 3 lines: simple count, LOD-heavy count, nested count.
5. **Sheet complexity top-10.** Nested bulleted list, not a markdown table (the chat surface does not render tables): one bullet per sheet with score and tier inline, e.g. "- Sheet Name, score 5, Moderate".
6. **Where to start reading.** 1-2 sentences. "Start with dashboard X, then calc Y."
7. **Known issues flag.** Default sheet names, orphan sheets, hidden sheets.
8. **Optional handoffs.** Line for each: "If you want a full metric dictionary, use data-scribe. If not installed, [manual fallback]."

Word count cap: 500.

## Output format (Complexity-score mode)

1. **All worksheets ranked by score.** Full list, not just top-10. Sort order (per `complexity-rubric.md` Tie-breaking and Edge cases): primary sort by score descending; within a tied score, sort by named-field-count on the sheet descending, then alphabetical by sheet name; hidden sheets sort to the bottom of the entire ranked list regardless of score (flag each as hidden inline).
2. **Per-sheet factor breakdown.** C1-C6 contribution per sheet as a nested bulleted list, not a markdown table (the chat surface does not render tables): one top-level bullet per sheet (score, tier) with a nested sub-bullet listing the C1-C6 contributions.
3. **Simple / moderate / complex buckets.** Count per bucket.

## Validation Gate

- **V1.** Workbook named explicitly (or workbook-level identifier if no name set).
- **V2.** Orient-mode output at or under 500 words (HC-2).
- **V3.** Every complexity score cites C1-C6 contributions (HC-4).
- **V4.** HC-3 short-circuit fires for workbooks under 5 sheets and 10 calcs.
- **V5.** Modified-date absence stated plainly if not available (HC-6).
- **V6.** No URLs pasted.
- **V7.** Routes to exhaustive skills carry manual fallbacks (HC-5).
- **V8.** Complexity scores are never framed as quality judgments (HC-8).

## Anti-patterns

- Running Orient mode on a trivial workbook (should short-circuit per HC-3).
- Exceeding 500 words in Orient mode.
- Inventing a C-factor not in C1-C6.
- Fabricating a modified-date when `get-workbook-inventory` returns none.
- Framing a complex worksheet as "bad" or "wrong" (HC-8).
- Running the full orient summary when the author triggered Complexity-score mode.
- Pasting a URL to any community resource.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. - **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

# Tableau Stakeholder Translator

Produces a plain-language translation of what a Tableau dashboard answers, in the voice of the stakeholder who will consume it. Scope-aware: names what the dashboard does NOT answer, so the author does not overclaim in the meeting.

## When to use (full trigger detail)

Translate a Tableau dashboard into plain language for a non-technical stakeholder. Produces a one-page translation layer. what this answers in plain words, what this does NOT answer, three likely follow-up questions, and the one chart that carries the headline. Audience-shaped voice from a locked 5-profile taxonomy (C-suite, business sponsor, operational manager, external customer, cross-functional peer). Read-only. Trigger on "translate this for my VP", "plain language version", "explain this to a non-analyst", "stakeholder version", "jargon-free summary", "what does this answer in their words". Do NOT trigger for. presenter scripts (route to dashboard-walkthrough-generator), metric dictionaries (route to data-scribe), handoff onepagers (route to workbook-summary-onepager), dashboard-level critique (route to viz-critique-pro-studio), authoring or editing anything in Desktop (out of scope).

## Reference files

- **`skill-expertise/stakeholder-voice-guide.md`.** Five locked audience profiles (C-suite, business sponsor, operational manager, external customer, cross-functional peer) with vocabulary rules and follow-up-question patterns.
- **`skill-expertise/jargon-swap-list.md`.** Common analyst-jargon terms with plain-language substitutions, keyed by audience profile.

## When to use

Author has built a technical dashboard and needs to describe it to a non-technical stakeholder. Wants a short rewrite plus the questions that stakeholder is likely to ask, not a design critique.

## Hard Constraints

- **HC-1 Read-only.** No mutation.
- **HC-2 Author declares audience before output.** Five locked profiles.
- **HC-3 Translation names structure and framing, never fabricates conclusions.** "This dashboard shows how our customer count has moved by region" is fine. "Customer growth is strong" is not.
- **HC-4 Honest "already plain" verdict.** If the dashboard labels and captions already read in plain language, say so and offer only the follow-up-question section.
- **HC-5 Required "What this does NOT answer" section.** Prevents overclaiming. The skill always surfaces at least one scope boundary even when the dashboard is clean.
- **HC-6 Standalone-safe routing.** Handoffs to dashboard-walkthrough-generator, data-scribe, workbook-summary-onepager all optional with manual fallbacks.
- **HC-7 Audience taxonomy locked.** No ad-hoc audience types.
- **HC-8 No pasted URLs to community resources.**

## Workflow

**Tools used.** `list-dashboards` (to enumerate dashboards and confirm which is the target), `list-worksheets` (to resolve zone-to-sheet mapping and identify sheets referenced in the translation), `list-available-fields` (to resolve technical field names for jargon-swap lookups and to identify data-source references for the Business sponsor voice), `get-dashboard-xml` (load-bearing read for current title, caption, label, and tooltip text; everything the translation actually swaps depends on this), `get-workbook-inventory` (to pull data-source names for the Business sponsor voice's "sourced from X" clarification; skip this call for C-suite and Operational manager audiences, which don't surface data-source detail by default).

**Why `get-dashboard-xml`, not `get-worksheet-xml`.** `get-worksheet-xml` has a confirmed 500/`operation-failed` risk on sheets that are already placed on a dashboard with real data (exactly the sheets this skill reads). `get-dashboard-xml` is used deliberately to avoid that failure mode, not as an oversight.

**General call-skipping rule.** Skip any read whose output the current branch cannot use. This already applies to `get-workbook-inventory` for C-suite/Operational audiences (above); it also applies to `list-available-fields` under the HC-4 "already plain" branch. If `get-dashboard-xml` text shows no analyst-jargon surfaces, do not call `list-available-fields` for jargon-swap lookups, since there is nothing left to swap.

**Mid-session audience change.** When the author asks for a different voice after already receiving output (see Error Handling table below), reuse the `get-dashboard-xml` read already in hand. Do not re-call it. Only the voice-dependent prose is regenerated.

Steps:

1. Call `list-dashboards`. Confirm target. If `list-dashboards` returns empty or errors, state so and offer to walk through the stakeholder-voice-guide as reading reference until a workbook is open.
2. Ask the author to declare the audience from the five locked profiles. Map any non-standard phrasing before proceeding.
3. Call `get-dashboard-xml` to read current title, caption, and tooltip text.
4. Apply the jargon-swap-list against identified technical terms.
5. Generate the five-section output.

## Audience taxonomy (locked)

Full detail in `skill-expertise/stakeholder-voice-guide.md`.

- **C-suite.** 1-2 minute attention budget. Headline only. Strategic follow-ups.
- **Business sponsor.** 3-5 minute budget. Named metrics with definitions. Follow-ups about expectations.
- **Operational manager.** 3-5 minute budget. What to do next. Follow-ups are tactical.
- **External customer.** 5-10 minute budget. Define everything. Follow-ups are clarifying.
- **Cross-functional peer.** 3-5 minute budget. Shared vocabulary from their function. Follow-ups are relational ("how does this affect my team").

## What it does

Two output paths. **Verified-fit path** reads the named target sheet via `get-worksheet-xml` to confirm prerequisites (continuous axis for W1/W2, time dimension on Columns for W3, continuous measure for W5) before emitting the recommendation. **General-recommendation path** proceeds on your question wording alone when you want a mechanism-level answer first; prerequisites are announced as unverified and you confirm fit before executing.

## Mechanism catalog summary (full catalog in mechanism-catalog.md)

- **W1 Reference line.** Static value drawn as a line on a continuous axis. Use for "target line," "break-even," "last-year baseline."
- **W2 Reference band.** Range drawn as a shaded band. Use for "acceptable zone," "quartile range," "forecast corridor."
- **W3 Trend line extension.** Linear or non-linear trend projection via Analytics pane. Use for "where will this be in 6 months at current rate." Must be flagged as projection, not prediction (HC-6).
- **W4 Set-based scenario.** Membership comparison via sets and set actions. Use for "customers who would move into the top-N if their revenue grew 10%."
- **W5 Dual-axis overlay.** Actual vs. hypothetical as two measures on the same chart. Use for "actual revenue vs. revenue if we hit target."
- **W6 Scenario calc.** Fixed-value calc field encoding a one-off hypothetical. Use for "revenue if every customer spent 20% more." Handed off to calc-writer for actual authoring.

If empty, aggregate dashboard titles from `get-dashboard-xml` across all dashboards — issue these as one batched pass over the dashboard list rather than one call per dashboard, and reuse the same batch for Section 4s dashboard enumeration instead of re-reading.
  2. Section 2 (Key metrics): if `calc_documentation/1` handoff is fresh, extract top 5 most-referenced calcs from the reference graph. If missing/stale, local-extract the primary datasources calc list via `list-available-fields` and rank by name-recency (weaker signal, labeled clearly).
  3. Section 3 (Data sources): if `data_model_documentation/1` handoff is fresh, extract per-DS summary. If missing/stale, local-extract from `get-workbook-inventory` datasource enumeration with `row_count: unknown` sentinel.
  4. Section 4 (Dashboards): if `caption_audit_report/1` handoff is fresh, extract dashboard names with title/caption presence flags. If missing/stale, local-extract dashboard names from `get-workbook-inventory` with `title_present: unknown` sentinels.
  5. Section 5 (Known limitations): parse workbook caption for a Known limitations: or Limitations: section. If absent, render empty-state prose.
- **Phase 3 Signal-Source Attribution.** For each section, populate `signal_source: handoff | local_extract | empty_state`. HC#5 requires transparent attribution; user must be able to tell where each fact came from.
- **Phase 4 Validate.** Run the 4-check V-gate: section coverage, signal-source attribution, ordering determinism, handoff completeness.
- **Phase 5 Deliver.** Two-tier: compact Tier A chat summary with all 5 sections in ~25 lines. Optional Tier B file save requires user path confirmation per HC#12 and format choice (`.md` or `.txt` only).

## Hard Constraints

**HC#1 Read-only against the workbook always.** Never mutates. File-write only for the onepager artifact (Tier B).

**HC#2 One workbook per run.** Multi-workbook runs refused.

**HC#3 5-section coverage locked.** No section omitted, no fabricated section added. Every section renders content or an empty-state prose fallback.

**HC#4 Refuse to fabricate.** No inferred metrics, no guessed row counts, no invented author intent. Sentinels: `null`, `unknown`, empty-state prose.

**HC#5 Signal-source labeled per section.** Every section emits `signal_source: handoff | local_extract | empty_state` so the reader can trace attribution. Never render a fact without stating its origin.

**HC#6 Author caption preserved verbatim.** If the workbook has an author caption (workbook-level or per-dashboard), its quoted byte-identical in the relevant section. Skill supplements around author intent; never rewrites or paraphrases.

**HC#7 Ordering determinism** (portfolio-wide HC#14). Section order locked (Section 1 → Section 5). Same input produces byte-identical output.

**HC#8 Diff-mode transparency** (portfolio-wide HC#13). Repeat invocations against unchanged workbook + handoff state emit `diff_mode: reused_verbatim` in Tier A. Fresh-scan / reused-verbatim / targeted-rescan enum.

**HC#9 Handoff-or-local labeled.** Every handoff-consuming section records which handoffs were fresh, which were stale, and which fell back to local-extract. `handoffs_consumed[]` and `handoffs_missing[]` populated in the report metadata.

**HC#10 Never silent file write.** Tier B save requires user path confirmation AND format choice (`.md` or `.txt`). No default writes to Downloads.

**HC#11 Empty-state prose over blank sections.** When a section has no data (no calcs, no dashboards, no author-declared limitations), render explicit empty-state prose (No calcs defined in this workbook, No known limitations documented in workbook caption) rather than a blank line.

**HC#12 Length cap.** Tier A output stays under 30 lines total across all 5 sections. Tier B is unbounded but structured per the same 5-section skeleton.

**HC#13 Handoff staleness detection required** (portfolio-wide HC#15). For each of the 3 upstream handoffs, verify workbook-fingerprint match against current state. Mismatch forces local-extract fallback for that section. Fingerprint mechanism verified sound during dashboard-tab-order behavioral run.

**HC#14 Reference-file grounding.** All 5 sections cite their detection criteria and worked examples in `skill-expertise/section_catalog.md`. Skill cites the reference file when a user challenges section content.

**HC#15 File format lock.** Tier B supports `.md` or `.txt` only. If user requests an unsupported format, skill refuses with a route to convert `.md` externally.

**HC#16 Wide-workbook scale handling.** For workbooks with 50+ calcs or 10+ dashboards, skill emits a wide-workbook-notice in Tier A (this workbook has N calcs and M dashboards; Section 2 truncates to top 5 by reference count, Section 4 truncates to top 10 dashboards, full list lands in Tier B). Truncation applies to Tier A only; Tier B is unbounded.

## Validation Gate (4-Check)

- **V1 Section Coverage.** All 5 sections rendered in locked order.
- **V2 Signal-Source Attribution.** Every section has `signal_source` populated per HC#5.
- **V3 Ordering Determinism.** Same workbook + same handoff state → byte-identical output per HC#7.
- **V4 Handoff Completeness.** `handoffs_consumed[]` and `handoffs_missing[]` populated. Fingerprint match verified for every consumed handoff.

## Common Mistakes (Anti-Patterns)

- **Fabricating row counts or metric values.** When `data_model_documentation/1` handoff is missing, emit `row_count: unknown` sentinel. Never guess.
- **Silently omitting a section.** HC#3 requires all 5 sections rendered. Empty-state prose per HC#11 for sections with no data.
- **Rewriting the author caption.** HC#6 preserves author intent verbatim. Skill supplements around it; never paraphrases.
- **Auto-invoking calc-documenter / data-model-documenter / dashboard-caption-audit.** Opportunistic consumption per HC#9; never chains-call upstream skills. User runs upstream skills separately if fresh handoffs are wanted.
- **Silent file write on Tier B save.** HC#10 requires path confirmation and format choice (`.md` or `.txt` only).
- **Requesting unsupported output format.** PDF, DOCX, HTML refused per HC#15. Route to external converter.
- **Ignoring handoff staleness.** HC#13 requires fingerprint verification. Stale handoff forces local-extract fallback, never silent stale-data rendering.

## Adjacent-Skill Routing

- **Upstream opportunistic:** `calc-documenter` (produces `calc_documentation/1`), `data-model-documenter` (produces `data_model_documentation/1`), `dashboard-caption-audit` (produces `caption_audit_report/1`).
- **Downstream opt-in:** `publish-readiness` (post-summary pre-publish sweep), `workbook-auditor` (summary delta tracking).
- **Refusal routes:** live-data snapshot → out of scope; workbook rewrites → `calc-writer` / `viz-planner`; tab-order audit → `dashboard-tab-order`; print-layout audit → `dashboard-print-check`; dashboard design scoring → `viz-critique-pro-studio`.

## Known Limitations

- **Live-data snapshot out of scope.** Summary is structural, not data-content. Section 2 lists metric definitions; not their current values.
- Supports `.md` and `.txt` only per HC#15.
- **Workbook-level author caption may not be exposed by all `get-workbook-inventory` implementations** in this environment. Section 1 falls back to dashboard-title aggregation if the caption is empty or unreadable.
- **`get-worksheet-xml` reliability gap on dashboard-bound sheets**. Section 4 dashboard enumeration may hit unreadable dashboards; skill emits `unknown` sentinel for those dashboards per HC#5.
- **DPC-style aspect-ratio and orientation properties are out of scope.** Section 4 lists dashboards by name and caption presence; layout details defer to `dashboard-print-check`.
- **`resolve-field` case-sensitivity concern** (a known platform gap, shared with calc-family skills). Section 2 metric-ranking uses handoff data preferentially to avoid triggering this gap.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.
