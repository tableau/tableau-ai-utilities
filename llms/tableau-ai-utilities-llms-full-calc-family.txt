# Calc Writer — when to use

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/calc-family/calc-writer

## What it does

Takes a natural-language ask, classifies the calc type (row-level, aggregate, LOD, table calc), looks up function signatures from a locked reference library (never guessed), authors via `author-calc`, verifies via `get-summary-data`, and passes an 8-check Validation Gate before delivery.

## When to use it

- "Write me a calc for revenue by customer."
- "Author a Boolean flag for orders over $500."
- "I need a calc that computes profit margin."
- "Create a rolling 90-day average sales calc."
- "Make a calc for days between order and ship date."

## When NOT to use it

- Debug a broken calc → use `calc-debugger`.
- Speed up a slow calc → use `calc-optimizer`.
- Translate SQL, Excel, or DAX to Tableau → use `calc-translator`.
- Style/naming audit → use `calc-linter`.
- List or catalog existing calcs → use `calc-inventory`.
- Ambiguous calc question → use `calc-orchestrator`.
- Create a parameter, set, or hierarchy → Desktop UI (out of scope).
- Build a dashboard or worksheet → `worksheet-builder` or `viz-planner`.

# Calc Writer

## When to use (full trigger detail)

Author a new Tableau calculated field from a natural-language ask. Single-calc-per-pass discipline by default, with an opt-in sequential multi-calc mode when the user is asked and agrees. Reads workbook via list-workbook-datasources and list-available-fields; writes via author-calc; verifies via get-summary-data. Every authored calc passes an 8-check Validation Gate (R-TYPE, R-AGG, R-LOD, R-TC, R-NULL, R-BOOL, R-PERF, R-NAME) before delivery. Signatures looked up from nested function library, never guessed. Triggers on "write this calc," "author a calc for," "I need a calc that," "create a calc for," "make a calc that." Do NOT trigger for debugging broken calcs (use calc-debugger), improving performance (use calc-optimizer), translating from SQL/Excel/DAX (use calc-translator), style/naming audits (use calc-linter), cataloging existing calcs (use calc-inventory), or ambiguous calc questions (use calc-orchestrator).

## Purpose

Author one new Tableau calculated field per run from a natural-language ask. Single-trigger discipline. Every calc passes an 8-check Validation Gate before delivery. Function signatures are looked up from the function library in `skill-expertise/`, never guessed. When another calc skill is chained, the handoff YAML (`calc_write_handoff/1`) passes the result along.

## Trigger Conditions

**Single-calc triggers (default mode):** "write this calc," "author a calc for," "I need a calc that," "create a calc for," "make a calc that," "build me a calc for," "give me a calc that."

**Multi-calc trigger (opt-in mode via HC#1 clarifier):** "write these calcs," "write me N calcs," "author several calcs," or any ask that names more than one calc in a single invocation. The skill still fires on the trigger, but HC#1s clarifier fires first ("one at a time or sequential this run?") before authoring begins.

**Adjacent-skill triggers that must NOT fire calc-writer:**

| Trigger phrase | Correct target skill |
|---|---|
| "debug this calc," "why is this calc returning NULL," "fix this broken calc" | `calc-debugger` |
| "optimize this calc," "why is this calc slow," "make this calc faster" | `calc-optimizer` |
| "translate this SQL to Tableau," "port this DAX to Tableau," "convert Excel formula" | `calc-translator` |
| "style-check my calcs," "lint my calcs," "check calc naming conventions" | `calc-linter` |
| "list all my calcs," "inventory these calcs," "catalog my calcs" | `calc-inventory` |
| "help with a calc" (ambiguous, no intent named) | `calc-orchestrator` |
| "build a dashboard," "create a viz for this calc" | `worksheet-builder` or `viz-planner` |
| "create a parameter for this calc" | Out of scope (author-parameter unreliable); route to Desktop UI. |
| "make this field a set" | Out of scope; route to Desktop UI. |
| "create a hierarchy from these calcs" | Out of scope; route to Desktop UI. |

## Scope Boundaries

- **IN:** author one new calc per run from a natural-language ask, or — when the user explicitly opts in via the HC#1 clarifier — a sequential multi-calc run authoring each named calc through the full pipeline one at a time; classify calc type (row-level, aggregate, LOD FIXED/INCLUDE/EXCLUDE, table calc); look up function signatures from `skill-expertise/` (function library files); run 8-check Validation Gate; verify output via `get-summary-data` on a scratch worksheet when the Verification Policy requires it; emit `calc_write_handoff/1` YAML only per HC#7.
- **OUT:** authoring multiple calcs without first asking the HC#1 clarifier; debugging existing calcs (`calc-debugger`); performance optimization (`calc-optimizer`); source-dialect translation (`calc-translator`); style audits (`calc-linter`); catalog exports (`calc-inventory`); parameter creation; set creation; hierarchy creation; whole-workbook migration; dashboard or worksheet building.

### Edge-Case Boundaries

| Edge Case | Handling |
|---|---|
| User asks for a calc that references a parameter | Author the calc, cite the parameter reference in the handoff as `[param_name] (parameter — cite but do not resolve)`. Do NOT attempt to create the parameter; refuse parameter creation. |
| User asks for a calc that references a set | Same as parameter: cite the set reference, refuse to create the set. |
| User asks for a calc that requires a nested calc dependency (`[Other Calc]`) that doesnt exist | Refuse the write; ask user to confirm whether to author the missing calc first (separate invocation) or use the raw fields inline. |
| User asks for a calc referencing a field that doesnt exist | Refuse: "field `[Missing Field]` doesnt exist in the target data source. Confirm the field name or point to the correct data source." Never fabricate the field. |
| User asks for a fresh parameter to be created for the calc | Refuse (author-parameter unreliable). Ask user to create the parameter manually in Desktop, then re-invoke. |
| Ambiguous calc type (could be row-level or aggregate) | Ask exactly one clarifier: "Should this aggregate across rows (SUM/AVG) or compute per row?" Never assume. |
| Sample size below 1,000 rows for verification | Report verification result but flag as "unverified: sample size below reliable threshold (1,000 rows)." Severity does not downgrade. |
| Data source has parameter-referencing calcs already (Data Scribe corruption risk) | Skip `build-and-apply-worksheet` verification; use existing scratch worksheet if one exists. Never mutate a workbook with parameter-referencing calcs via shelf-mutating tools. |
| Fresh-parameter resolution failure (author-calc cant resolve a param by bare name) | Retry once after asking user to refresh the Data pane in Desktop. If still failing, refuse with manual calc-creation instructions (platform gap). |
| Very wide data source (>100 fields) | Batch `list-available-fields` in groups of ~10 with inline progress notes. Reuse Phase 1 inventory across chained invocations in the same session rather than re-batching per call. |
| Multi-table data source (relationships or cross-join scenarios) | Confirm which logical table the calc will reference before authoring. If the calc spans two related tables, verify cardinality context in the handoff notes (calcs grain matters at query time). |
| Very narrow data source (<10 fields) | Skip the batching guidance in Phase 1; single `list-available-fields` call sufficient. |
| Tiny extract (<sample_size rows) | Sample size threshold labeling applies; report verified findings but flag confidence with "unverified: sample size below reliable threshold (1,000 rows)." |
| Ambiguous field name shared across multiple data sources | When asking which source, name each candidate source alongside the fields role/type in that source (e.g., "measure" vs. "dimension") so the user isnt just repeating the field name back — clarify with data-source names, not field names, since the field name alone doesnt disambiguate. |

## Hard Constraints

- **HC#1:** Default mode authors exactly one calc per run. If the ask names multiple calcs in one invocation, ask exactly one clarifier before starting: "I can author these one at a time (default, re-invoke per calc) or walk through all N sequentially in this run as separate single-calc passes — which would you prefer?" Never assume multi-calc mode; the user must opt in per invocation. In multi-calc mode, each calc still runs the full pipeline (Phases 0-4.6) independently and in sequence — no batching or shortcutting of field verification or the V-gate; Phase 4 verification follows the Verification Policy for each calc. A failure on one calc in the sequence does not block the others; report per-calc results.
- **HC#2:** Function signatures are looked up from `skill-expertise/INDEX.md`, never guessed. If the function isnt in the library, refuse the write; do not invent a signature.
- **HC#3:** Every authored calc passes the full 8-check Validation Gate (`skill-expertise/validation_gate.md`) before delivery. Failing any gate blocks the write.
- **HC#4:** One clarifying question maximum. If the ask is ambiguous, ask exactly one clarifier. Never chain a second.
- **HC#5:** Never fabricate field references. If a named field doesnt exist in the target data source, refuse.
- **HC#6:** Never create parameters, sets, or hierarchies. Refuse and route to Desktop UI manual creation.
- **HC#7:** Emit `calc_write_handoff/1` YAML only when the user chains to another installed calc skill or asks for it. Never include it in the normal user-facing reply.
- **HC#8:** Refuse out-of-scope questions by exact slug (six calc-family peers + `worksheet-builder`/`viz-planner` for dashboard work).
- **HC#9:** Perf advisory is advisory-only. Never rewrite the calc for performance. Detect patterns per the perf-advisory catalog, surface the recommendation in the reply with a verbatim `calc-optimizer` trigger phrase (and in `perf_advisory` when a handoff is emitted). Optimization is `calc-optimizer`s job.
- **HC#10:** Never claim quantified perf impact (specific latency, row count, or memory reduction). Perf advisory is pattern-detection only. Quantified impact comes from `calc-optimizer`, which profiles against actual data.

## Tools Used

- `list-workbook-datasources` — Phase 0 (identify target DS).
- `list-available-fields` (verbosity: full) — Phase 1 (verify field references, check for parameter-corruption risk).
- `author-calc` — Phase 3 (write the calc).
- `add-worksheet`, `delete-sheet` — Phase 4 (create/clean scratch worksheet for verification).
- `add-field` — Phase 4 (place calc on scratch worksheet Detail).
- `get-summary-data` — Phase 4 (verify calc output).
- `resolve-field` — Phase 1 fallback (disambiguate field names).

One workbook mutation per run (the authored calc, plus a scratch worksheet only when the Verification Policy calls for Phase 4). Any scratch worksheet is cleaned in Phase 5.

## Function Library (Locked Reference)

`skill-expertise/INDEX.md` catalogs ~150 Tableau Studio functions across eight categories: string, date, number, logical, aggregate, LOD, table calc, spatial. Every function has a signature, return type, LOD/TC eligibility, and version-gated status (e.g., MAKEPOINT 2019.2+, BUFFER 2024.1+, USEREMAIL 2023.3+).

Never invent a signature.

### Domain-Accuracy Assertions (Locked)

Locked Tableau behaviors (LOD order of operations, ATTR failure modes, INT vs. ROUND, Boolean aggregation, COUNT/COUNTD NULLs, DATEPARSE patterns, table-calc partitioning, spatial and USEREMAIL version gates, REGEXP escaping) live in `skill-expertise/domain_accuracy.md`. Read it before authoring any LOD, table-calc, ATTR, Boolean-aggregate, date-parsing, spatial, or REGEXP calc. Any calc that violates an assertion is caught by the Validation Gate or a perf-advisory flag, never delivered.

## Validation Gate (Locked, 8 Checks)

Every authored calc passes all applicable checks in `skill-expertise/validation_gate.md` before delivery, in this order: R-TYPE-01/02, R-AGG-01/02, R-LOD-01/02/03 (LOD only), R-TC-01/02 (table calc only), R-NULL-01, R-BOOL-01, R-PERF-01, R-NAME-01. Any failure blocks the write. If R-TYPE-01 fails, re-classify before re-authoring; other failures may need a clarifier or refusal.

## Sample-Size Reliability Threshold

`get-summary-data` verification is reliable when the scratch worksheet returns at least **1,000 rows**. Below that threshold:

- Report the verification result normally.
- Flag as **"unverified: sample size below reliable threshold (1,000 rows)."**
- Severity does not downgrade; the confidence label changes.

## Scale Tiers, Multi-Calc Mode, and Source Types

Field-count tiers (narrow to 200+ fields), row-count confidence tiers, multi-calc sequential mode, and data source type branching (extract, live, blend, federated, multi-table) are in `skill-expertise/scale_and_modes.md`. Read it for 100+ field or 1M+ row sources, multi-calc runs, or any blended, federated, or multi-table source.

## Verification Policy (When to Run Phase 4)

Run the scratch-sheet check (Phase 4) only when it is worth the extra calls:

- **Verify:** LOD (FIXED/INCLUDE/EXCLUDE), table calc, any ATTR or mixed row-level/aggregate logic, DATEPARSE or date math, type conversion, REGEXP, a nested-calc dependency, or when the user asks to check it.
- **Skip:** simple row-level calcs (arithmetic, comparisons, IF/CASE on existing fields, string concatenation) once `author-calc` succeeds and the Validation Gate passes.
- **Can't verify:** a FIXED LOD with no dimensions does not return through `get-summary-data` (platform gap). Report it as not checked in a view.
- **Never** verify on a data source with parameter-referencing calcs (shelf-mutation corruption risk); report it as not checked in a view.

Always state which happened in the reply: "Checked on N rows" or "Not checked in a view yet. Say 'check it' to verify on your data." Never imply a check that did not run.

## Workflow Phases

1. **Phase 0 Intake.** Confirm target data source via `list-workbook-datasources`. If multi-source, ask which. Parse the users natural-language ask into an intent: measure, dimension, calc-type hint, expected return type. If the ask names more than one calc, apply HC#1s clarifier before proceeding.
2. **Phase 1 Field Verification.** Call `list-available-fields` (verbosity: full). Verify every field the ask references exists. If any missing, refuse per HC#5. Check for parameter-referencing calcs already in the data source (parameter-corruption avoidance).
   - **Wide-workbook batching:** on data sources with >100 fields, batch `list-available-fields` calls in groups of ~10 with inline progress notes. Skip on <100-field sources.
   - **Inventory reuse:** if the same session already ran Phase 1 on this data source (e.g., a prior calc-writer invocation, or a chained handoff from calc-optimizer / calc-linter), reuse the cached inventory rather than re-calling. Detect this by checking whether the previous handoffs `datasource_name` matches the current target.
3. **Phase 2 Function Lookup.** For every function the calc requires, look up the signature in `skill-expertise/INDEX.md`. If missing, refuse per HC#2. If found, note the version-gated status if any.
4. **Phase 3 Author.** Call `author-calc` with the composed formula. On success, capture the returned calc name and formula text. On failure, apply error-handling table.
5. **Phase 4 Verification (conditional, per the Verification Policy).** Skip this phase for simple row-level calcs and report "not checked in a view yet." Otherwise, create a scratch worksheet (if none exists). Reference the calc on the shelf using the correct derivation prefix, determined by whether the calcs own formula already contains an aggregation:
   - **Formula has no aggregation** (plain row-level calc, e.g. `DATEDIFF(...)`, `[Sales] > 500`): Tableau applies default aggregation on shelf placement. Use `none:` for a dimension-role calc, `sum:` for a measure-role calc.
   - **Formula already contains its own aggregation** (`SUM(...)`, `AVG(...)`, an LOD `{FIXED/INCLUDE/EXCLUDE ...}`, or a table calc): the calc is fully aggregated already and has no separate per-row instance to re-aggregate. Use its native `usr:` ref — never wrap it in an additional `sum:`, which Tableau will reject as "no field named" the moment you try.
   - Either way, place the calc alone on Detail with nothing else on the shelves for verification, then call `get-summary-data`. Apply sample-size threshold labeling. If scratch worksheet creation fails, retry once; if it fails a second time, mark `verified: false`, `sample_size: "verification_skipped"`, and note the failure in the handoff rather than blocking delivery of an otherwise-passing calc.
   - **Table-calc addressing dimension:** when verifying a table calc that depends on row order (WINDOW_*, RUNNING_*, PREVIOUS_VALUE, INDEX, RANK, LOOKUP), place a continuous date pill (e.g., `[tdy:Order Date:qk]` or the appropriate continuous truncation) on Rows for the addressing dimension — never the raw discrete date field, which fails preflight as `date-field-bound-as-string`.
6. **Phase 4.4 Perf-Advisory Scan.** Pattern-match the authored calc against the perf-advisory catalog in `skill-expertise/handoff_schema.md` (PA-COUNTD-HIGH-CARDINALITY, PA-REGEXP-IN-AGGREGATE, PA-CONTAINS-IN-AGGREGATE, PA-LOD-NESTED, PA-TABLE-CALC-WHERE-LOD-WOULD-WORK, PA-CROSS-DS-BLEND, PA-DATEDIFF-IN-FILTER, PA-NESTED-IF-DEEP, PA-STRING-ARITHMETIC). This is advisory-only. Never rewrite the calc for perf; thats `calc-optimizer`s job. If severity is `note` or `warning`, tell the user in one line with the verbatim `calc-optimizer` trigger phrase. When a handoff is emitted (HC#7), also populate `perf_advisory.flags`, `perf_advisory.severity`, and `perf_advisory.recommendation`.
7. **Phase 4.5 Validation Gate.** Run all 8 checks against the authored calc. Any failure blocks delivery. If R-TYPE-01 fails, re-classify and re-author. Other failures may require clarifier or refusal.
8. **Phase 4.6 Disagreement Branch (conditional).** If user disputes the delivered calc:
   - Offer one alternate formulation (typically the next-most-natural calc type: row-level → aggregate, aggregate → LOD FIXED, or vice versa).
   - If rejected, route to Tableaus calc reference docs. Never chain a second alternate.
9. **Phase 5 Cleanup + Reply.** Delete any scratch worksheet (or leave it with the users approval). Reply with: the calc name and formula, what it does in one line, the verification status ("Checked on N rows" or "Not checked in a view yet"), and any perf note. Emit `calc_write_handoff/1` only per HC#7.

## Handoff Contract

The `calc_write_handoff/1` YAML schema is in `skill-expertise/handoff_schema.md`. Emit it only per HC#7: when the user chains to another calc skill that is installed in this session ("now optimize it", "now lint it", "add it to the inventory") or explicitly asks for it. It is not part of the normal reply. Downstream skills refuse unknown schema versions.

| Situation | Response |
|---|---|
| Multi-source workbook | Ask which source. If the ask also names multiple calcs, combine with the HC#1 clarifier (one-at-a-time vs. sequential multi-calc mode) rather than asking twice. |
| Field doesnt exist in the target DS | Refuse per HC#5. Ask user to confirm field name or point to correct DS. |
| Function isnt in the library | Refuse per HC#2. Never invent a signature. |
| Ambiguous calc type | Ask one clarifier per HC#4. Never chain a second. |
| Parameter reference in the ask, parameter doesnt exist | Refuse parameter creation per HC#6. Ask user to create manually in Desktop, then re-invoke. |
| Fresh-parameter resolution fails (author-calc cant resolve param by bare name) | Retry once after Data pane refresh. If still failing, refuse with manual calc-creation instructions. |
| `author-calc` returns "syntax error" | Diagnose via V-gate rules; if fixable, re-author with corrected formula; else refuse and hand off to `calc-debugger`. |
| `author-calc` returns success but `get-summary-data` verification shows wrong output | Re-run V-gate; if V-gate says calc is valid but semantics dont match ask, offer one alternate formulation per Phase 4.6. |
| Data source has parameter-referencing calcs (corruption risk) | Skip `build-and-apply-worksheet`; use existing scratch worksheet. Never shelf-mutate. |
| Validation Gate R-TYPE-01 fails | Re-classify calc type; re-author once. If second attempt fails, refuse. |
| Validation Gate any other rule fails | Report the specific rule ID and evidence; block delivery. |
| User asks for multiple calcs in one invocation | Ask the HC#1 clarifier (one-at-a-time vs. sequential multi-calc mode this run). Proceed per the users choice; never assume. |
| Field or parameter reference resolves at Phase 1 but fails to resolve at `author-calc` time (stale/renamed mid-session) | Retry once. If still failing, refuse with "field/parameter `[X]` no longer resolves; confirm it wasnt renamed or removed, or refresh the Data pane and re-invoke." Do not silently substitute a similarly-named field. |
| User asks for debugging/optimization/translation/lint/inventory | Route to exact slug per HC#8. |
| `author-calc` hangs/times out twice in a row (no dialog blocking, session confirmed reachable) | Stop retrying after the second timeout. Check whether the calc was actually created server-side despite the timeout (search the field inventory for the intended caption) before assuming failure. If genuinely not created, hand the user exact manual creation steps (caption, formula, datatype, role) for Desktops Create Calculated Field dialog, and explicitly ask them to confirm once done so verification can proceed — never let the handoff trail off without that ask. Confirmed not connection-type-dependent: the same hang recurred identically on both a live connection and its extracted version of the same data source, and survived a full Desktop restart — treat this as a standing environment reliability gap, not a live-connection-latency or stale-session issue. |

## Common Mistakes to Avoid

- Inventing a function signature that isnt in `INDEX.md`. HC#2 hard-bans.
- Authoring a calc without running the full 8-check V-gate. HC#3 hard-bans.
- Fabricating field references. HC#5 hard-bans.
- Attempting to create a parameter. HC#6 hard-bans; route to Desktop UI.
- Chaining clarifying questions past the first. HC#4 caps at one.
- Emitting the handoff YAML when no calc skill asked for it, or showing it in the normal reply. HC#7 limits it to chained runs.
- Building a scratch sheet for a simple row-level calc. The Verification Policy skips it.
- Implying a calc was checked when Phase 4 did not run. Always state the verification status.
- Hedging on calc type ("this might be an LOD"). Classify or refuse.
- Delivering a calc that references a non-existent nested calc. Refuse per Edge-Case Boundary.
- Treating an `author-calc` "success" response as proof only the intended calc changed. If the returned calc name, formula, or datasource doesnt match what was requested, stop and verify before delivering — `author-calc` can silently touch the wrong calc on a workbook with caption collisions or stale field references; never assume success implies isolation.
- Assuming multi-calc mode by default. HC#1 requires the clarifier every time multiple calcs are requested in one invocation.

## Known Limitations

- Default mode is one calc per invocation; sequential multi-calc mode requires explicit user opt-in per HC#1 and still runs each calc through the full pipeline (no shortcuts). True batch authoring (parallel writes, shared V-gate pass) remains out of scope.
- Parameter creation is out of scope (platform gap).
- Set and hierarchy creation are out of scope.
- Function library reflects Tableau Desktop 2026.x GA.
- Fresh-parameter resolution has a documented one-retry pattern (platform gap).
- Sample-size threshold labeling requires ≥1,000 rows for verified; smaller samples flag as unverified.
- Simple row-level calcs are not checked in a view by default (Verification Policy); users can ask for a check.
- Version-gated functions (MAKEPOINT 2019.2+, BUFFER 2024.1+, USEREMAIL 2023.3+) noted inline; older Desktop versions may not support them.

## MCP Skill Mapping

`tableau-calc-engine` (Cloud) is the analog. Calc Writer is the Desktop-agent-native single-trigger authoring peer.

## Relationship to Other Skills

- **Peer to `calc-debugger`, `calc-optimizer`, `calc-translator`, `calc-linter`, `calc-inventory`.** Single-trigger discipline enforced by explicit Do NOT trigger clauses.
- **Orchestrator:** `calc-orchestrator` routes ambiguous asks to Calc Writer when intent is clearly "author new."
- **Downstream handoff (only when chained, per HC#7):** `calc_write_handoff/1` YAML consumable by `calc-optimizer` ("now optimize it"), `calc-linter` ("now lint it"), `calc-inventory` ("now include this in the catalog").
- **Upstream:** `viz-planner` and `worksheet-builder` may invoke Calc Writer during dashboard design when a calc is needed.
- **Sibling to non-calc skills:** never authors a field alias (thats a Desktop UI action); never modifies the data model (`join-and-relationship-advisor`); never documents field meaning (`data-scribe`).

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

# Calc Debugger — when to use

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/calc-family/calc-debugger

## What it does

Takes a broken calc, reads its actual formula, classifies the failure against a locked 9-pattern error catalog (E-NULL through E-CIRC), proposes a corrected version, re-authors via `author-calc`, verifies via `get-summary-data`, and passes the same 8-check Validation Gate as calc-writer before delivery.

## When to use it

- "Debug this calc — it returns NULL for some customers."
- "Why is my profit margin calc showing negative values?"
- "This calc errors on `SUM([Sales]) / [Rows]` — fix it."
- "My LOD returns the wrong grain, help me fix it."
- "This calc had a syntax error after I edited it."

## When NOT to use it

- Write a brand-new calc → use `calc-writer`.
- Speed up a working calc → use `calc-optimizer`.
- Translate SQL, Excel, or DAX to Tableau → use `calc-translator`.
- Style/naming audit → use `calc-linter`.
- List or catalog existing calcs → use `calc-inventory`.
- Ambiguous calc question → use `calc-orchestrator`.
- Grain/join model issue where the calc is a symptom → use `join-and-relationship-advisor` first, then come back for the calc fix.

# Calc Debugger

## When to use (full trigger detail)

Diagnose why an existing Tableau calculated field is broken (returns NULL, wrong values, syntax error, silent failure) and propose a corrected version. Single-calc-per-pass discipline by default, with an opt-in sequential multi-calc mode when the user is asked and agrees. Reads workbook via list-workbook-datasources and list-available-fields; reads the broken formula; classifies the failure against an error-pattern catalog; proposes fix; re-authors via author-calc; verifies via get-summary-data. Triggers on debug this calc, why is this calc returning NULL, fix this broken calc, why does this calc error. ## Purpose

Diagnose one broken Tableau calculated field per run, propose a corrected version, re-author, and verify. Single-trigger discipline. Every fix passes the same 8-check Validation Gate as calc-writer. Error-pattern classification is looked up from a nested error-pattern catalog, never guessed. Handoff YAML (`calc_debug_handoff/1`) makes the result consumable by downstream peers.

## Trigger Conditions

## Scope Boundaries

- **IN:** diagnose one broken calc per run (or sequential N via HC#1 opt-in), classify against error-pattern catalog (E-NULL, E-SYNTAX, E-TYPE, E-AGG, E-LOD, E-FIELD, E-PARAM, E-GRAIN, E-CIRC), propose corrected formula, re-author via `author-calc`, verify via `get-summary-data`, run full 8-check Validation Gate on the fix, emit `calc_debug_handoff/1` YAML.
- **OUT:** authoring brand-new calcs from scratch (`calc-writer`); performance-only concerns when the calc functionally works (`calc-optimizer`); source-dialect port (`calc-translator`); style/naming audits (`calc-linter`); catalog exports (`calc-inventory`); parameter/set/hierarchy creation; whole-workbook migration; dashboard building; fixing the data model when the calc is a symptom of a grain/join issue (route to `join-and-relationship-advisor` first).

### Edge-Case Boundaries

| Edge Case | Handling |
|---|---|
| Broken calc references a field that no longer exists | Classify as E-FIELD. Propose fix that either (a) substitutes a similarly-named real field per user confirmation, or (b) refuses if no close match. Never silently substitute. |
| Broken calc references a parameter that no longer exists | Classify as E-PARAM. Refuse re-authoring; ask user to recreate the parameter in Desktop UI first. |
| Broken calc has R-AGG-01 violation (bare field in aggregate context) | Classify as E-AGG. Auto-correct by wrapping with SUM/AVG/etc. Same self-healing path as calc-writer's R-AGG-01. |

| Ambiguous failure (calc returns wrong value but formula looks fine) | Ask exactly one clarifier: what value are you expecting, and what value are you seeing? Never assume the correct answer. |
| Very wide data source (>100 fields) | Batch `list-available-fields` in groups of ~10 with inline progress notes. Reuse Phase 1 inventory across chained invocations in the same session. |
| Multi-table data source (relationships or cross-join scenarios) | Confirm which logical table the calc references before diagnosing. Grain-related failures may route to `join-and-relationship-advisor`. |
| Sample size below 1,000 rows for verification | Report verification result but flag as unverified: sample size below reliable threshold (1,000 rows). Severity does not downgrade. |
| Data source has parameter-referencing calcs already (Data Scribe corruption risk) | Skip `build-and-apply-worksheet` verification; use existing scratch worksheet if one exists. Never mutate a workbook with parameter-referencing calcs via shelf-mutating tools. |
| `author-calc` hangs twice on the fix attempt | Per portfolio-wide pattern: stop retrying after 2 timeouts. Check if the fix actually landed server-side by querying field inventory. If not, hand off manual fix steps to the user with explicit confirm when done for verification. |
| Original broken calc has R-AGG-01 self-healing scope | Auto-correct per V-gate; note the specific violation in handoff `notes`. |

## Hard Constraints

- **HC#1:** Default mode debugs exactly one calc per run. If the ask names multiple broken calcs in one invocation, ask exactly one clarifier before starting: I can debug these one at a time (default, re-invoke per calc) or walk through all N sequentially in this run as separate single-calc passes — which would you prefer? Never assume multi-calc mode. In multi-calc mode, each calc runs the full pipeline (Phases 0-4.6) independently and in sequence; failure on one doesn't block the others.
- **HC#2:** Function signatures are looked up from `skill-expertise/INDEX.md`, never guessed. Same discipline as calc-writer.
- **HC#3:** Every proposed fix passes the full 8-check Validation Gate (`skill-expertise/validation_gate.md`) before delivery. Failing any gate blocks the fix.
- **HC#4:** One clarifying question maximum. Never chain a second.
- **HC#5:** Never fabricate field references. If a named field doesn't exist, classify as E-FIELD and refuse silent substitution.
- **HC#6:** Never create parameters, sets, or hierarchies, even though `author-parameter` exists: debugging fixes existing calcs and does not add new workbook objects. If a broken calc references a missing parameter, refuse, cite HC#6 ("calc-debugger doesn't create parameters"), and route to Desktop UI. Never say the agent can't create parameters.
- **HC#7:** Emit `calc_debug_handoff/1` YAML on every successful fix, whether downstream requested or not.
- **HC#8:** Refuse out-of-scope questions by exact slug (six calc-family peers + `join-and-relationship-advisor` for grain/model concerns + `worksheet-builder`/`viz-planner` for dashboard work).
- **HC#9:** Never diagnose without reading the actual broken formula. If the user only describes the symptom without pasting the formula, ask for it (single clarifier per HC#4).
- **HC#10:** Never fix a symptom that's actually caused by a model issue. If diagnosis identifies grain/join/fanning as the root cause, route to `join-and-relationship-advisor` for the model fix; return for the calc fix only after the model is resolved.

## Error-Pattern Catalog (Locked)

`skill-expertise/error_patterns.md` catalogs 9 error patterns. Every diagnosis cites the specific pattern ID.

| Pattern ID | Signature | Root Cause | Fix Approach |
|---|---|---|---|
| E-NULL | Calc returns NULL when non-NULL expected | Field NULL propagation, missing IFNULL/ZN, filter mismatch | Wrap with ZN, IFNULL, or add ISNULL fallback |
| E-SYNTAX | `author-calc` rejects with syntax error | Malformed function call, unmatched brackets, wrong function name | Refactor per function library signature |
| E-TYPE | Return type doesn't match usage context | String returned where Number expected, Boolean returned where Number expected | Explicit type conversion (INT, STR, FLOAT, BOOL) |
| E-AGG | R-AGG-01/02 violation | Bare field in aggregate context, ATTR-based Boolean | Wrap with SUM/AVG (R-AGG-01) or rewrite to MIN/MAX (R-AGG-02) |
| E-LOD | LOD returns wrong grain | Missing dimension, wrong LOD type, filter-order confusion | Adjust dimensions, switch FIXED/INCLUDE/EXCLUDE, or promote filter to context |
| E-FIELD | Reference to nonexistent field | Field deleted, renamed, or from a different data source | Refuse silent substitution; ask user to confirm intended field |
| E-PARAM | Reference to nonexistent parameter | Parameter deleted or renamed | Refuse re-authoring; route to Desktop UI parameter recreation |
| E-GRAIN | Wrong values due to fanning or grain mismatch | Many-to-many join, wrong logical table, missing FIXED LOD | Root cause may be model; route to `join-and-relationship-advisor` first if diagnosis warrants |
| E-CIRC | Circular reference chain | Calc A refs Calc B refs Calc A (direct or indirect) | Refuse re-authoring; report cycle, ask user to break manually |

### Domain-Accuracy Assertions (Locked, Debugger-Specific)

Every diagnosis leverages these locked Tableau-specific behaviors. Cited from `help.tableau.com`; each rule maps to a specific error pattern.

- **NULL propagation semantics** (E-NULL diagnosis): any arithmetic operation with a NULL operand returns NULL. Comparison with NULL (e.g., `[Field] = NULL`) is itself NULL, not TRUE or FALSE. Use `ISNULL([Field])` for NULL checks.
- **Divide-by-zero returns NULL, not error** (E-NULL): `SUM([Numer]) / SUM([Denom])` where SUM([Denom])=0 returns NULL silently. Diagnose with `IF SUM([Denom]) = 0 THEN NULL ELSE ... END` explicit guard.
- **ATTR failure modes** (E-AGG, R-AGG-02): `NOT ATTR([BoolField])` returns NULL when values are mixed within the group. `ISNULL(ATTR([DimField]))` returns TRUE both for genuinely-NULL and mixed-value groups. Prefer MIN/MAX for stable-scalar semantics. Locked decision rule (see `skill-expertise/error_patterns.md` E-AGG): ATTR stays only when diagnosis confirms mixed-value groups genuinely exist AND the calc's semantics require a NULL-on-disagreement signal; otherwise rewrite to MIN/MAX. A reported NULL is itself evidence the rewrite condition is not met.
- **LOD order of operations** (E-LOD, R-LOD-03): FIXED executes before dimension filters; INCLUDE/EXCLUDE execute after. Context filters promote a dimension filter to run before FIXED. This is a common cause of the calc looks fine but returns unexpected values when I filter E-LOD diagnoses.
- **DATEPARSE case sensitivity** (E-SYNTAX): Java SimpleDateFormat requires capital `MM` for month; lowercase `mm` is minutes. Excel-style `'yyyy-mm-dd'` misparses in Tableau. This is a common E-SYNTAX root cause.
- **Boolean-as-Integer aggregation** (E-TYPE): Tableau implicitly casts TRUE→1 and FALSE→0 inside SUM. `SUM(IF ... THEN 1 ELSE 0 END)` and `SUM(IF ... THEN 1 END)` are both valid counting patterns. Diagnose E-TYPE only when the outer context expects a different type than what the calc returns.
- **INT truncates, does not round** (E-TYPE): `INT(2.7) = 2`, not 3. Use ROUND if rounding is intended.
- **COUNT vs. COUNTD NULL handling** (E-NULL context): both ignore NULL by default. If NULLs should count, wrap with IFNULL or count a Boolean flag.
- **Table-calc partitioning defaults** (E-LOD adjacent): default partitioning is by every dimension in the view; explicit compute using / along required for reproducibility. calc-debugger fixes to table calcs must document partitioning intent in `notes` per R-TC-01.
- **Fanning on many-to-many joins** (E-GRAIN): SUM/AVG on shelf-placed measures doubles when Orders is joined many-to-many to Returns via Order ID. Root cause is model; fix is `{FIXED [Order ID] : SUM([Sales])}` after `join-and-relationship-advisor` confirms the relationship is correct.
- **Fresh-parameter resolution failure** (E-PARAM adjacent): author-calc may fail to resolve a freshly-created parameter by bare name until Desktop's Data pane refreshes (platform gap). One retry after refresh; refuse if still failing.
- **Version-gated functions** (E-SYNTAX adjacent): MAKEPOINT 2019.2+, MAKELINE 2019.2+, DISTANCE 2019.2+, INTERSECTS 2019.2+, AREA 2020.4+, LENGTH 2020.4+, CENTROID 2022.4+, BUFFER 2024.1+, USEREMAIL 2023.3+. Older Desktop versions may reject these with a function not recognized error that classifies as E-SYNTAX.

Any diagnosis that violates one of these assertions gets caught by the corresponding V-gate rule or is explicitly cited in the handoff `notes`.

### Multi-Calc Sequential Mode (Debugger-Specific)

Multi-calc mode (HC#1 opt-in) runs the full pipeline per broken calc, one at a time. Explicit runtime characteristics:

- **N calcs = N inventory reuses.** Phase 1 inventory reused across the sequence.

## Workflow Phases

1. **Phase 0 Intake.** Confirm target data source via `list-workbook-datasources`. Identify the broken calc by name. If user only describes the symptom without naming the calc, ask one clarifier per HC#4 + HC#9. If ambiguous field or role/type across multiple sources, apply calc-writer's Fix 1 pattern: name each candidate source with role/type.
2. **Phase 1 Read + Field Verification.** Call `list-available-fields` (verbosity: full). Read the broken calc's actual formula from the field inventory. Verify every field the formula references still exists. If any missing, classify as E-FIELD per HC#5.
   - **Wide-workbook batching:** on >100-field data sources, batch in groups of ~10.
   - **Inventory reuse:** reuse Phase 1 inventory across chained invocations in the same session.
3. **Phase 2 Error-Pattern Classification.** Match the observed failure (from user's report + tool output) against the error-pattern catalog (E-NULL through E-CIRC). If no pattern matches cleanly, ask one clarifier per HC#4 to narrow. Never guess.
4. **Phase 3 Fix Author.** Compose the corrected formula per the pattern's fix approach. Call `author-calc` with the fix as a new caption `[original name] Fixed` (default) unless user opts to overwrite the original. On success, capture the returned calc name and formula. On failure, apply error-handling table.
5. **Phase 4 Verification.** Per the corrected verification-derivation-prefix rule (revised 2026-09-06): check whether the fixed calc is **AGG-flagged** in `list-available-fields` (not merely whether its formula string contains an aggregation function). If AGG-flagged, use the native `usr:` ref (never wrap in `sum:`). If not AGG-flagged — including a plain FIXED-LOD or aggregate-expression calc being placed on a shelf like any other measure — use `none:` (dimension) or `sum:` (measure) per Tableau's default role. The earlier rule (formula contains SUM()/LOD → always usr:) was too broad: a FIXED LOD calc's *formula* contains its own aggregation, but the calc itself still gets `sum:` when dropped onto a shelf, same as any other measure. Never invent a derivation prefix — resolve it via `resolve-field` or `list-available-fields` before placing. Create scratch worksheet (if none exists), place the fixed calc on Detail with the correct ref, call `get-summary-data` to verify output.
   - **Fail-open policy:** if scratch worksheet creation fails twice, mark `verified: false, sample_size: verification_skipped` and note the failure. Do not block delivery.
   - **Table-calc verification:** table calcs need a continuous date pill (e.g., `[tdy:Order Date:qk]`) for the addressing dimension, never the raw discrete date field.
   - **`author-calc` hang recovery:** if `author-calc` hangs twice on the fix, stop retrying. Check if the fix landed server-side by querying inventory. If not, hand off manual creation steps to the user with explicit confirm when done for verification.
6. **Phase 4.4 Perf-Advisory Scan.** Same pattern-match as calc-writer (PA-COUNTD-HIGH-CARDINALITY, PA-REGEXP-IN-AGGREGATE, PA-CONTAINS-IN-AGGREGATE, PA-LOD-NESTED, PA-TABLE-CALC-WHERE-LOD-WOULD-WORK, PA-CROSS-DS-BLEND, PA-DATEDIFF-IN-FILTER, PA-NESTED-IF-DEEP, PA-STRING-ARITHMETIC). Advisory-only. Populate `perf_advisory` in the handoff.
7. **Phase 4.5 Validation Gate.** Run all 8 checks against the fixed calc. Any failure blocks delivery.
8. **Phase 4.6 Disagreement Branch (conditional).** If user disputes the delivered fix:
   - Offer one alternate fix approach (e.g., E-NULL could be fixed with ZN or IFNULL; offer the alternate).
   - If rejected, route to Tableau's calc reference docs. Never chain a second alternate.
9. **Phase 5 Cleanup + Handoff.** Delete scratch worksheet (or leave with user's approval). Emit `calc_debug_handoff/1` YAML with `perf_advisory` section populated from Phase 4.4.

## Common Mistakes to Avoid

- Diagnosing without reading the actual broken formula. HC#9 requires reading.
- Fabricating an error pattern outside E-NULL through E-CIRC. HC#2 requires catalog lookup.
- Silently substituting a similar field name for a missing one. HC#5 refuses.
- Auto-overwriting the original broken calc without user consent. Default is `[original name] Fixed`; overwrite only on opt-in.
- Skipping V-gate on the fix. HC#3 requires it.
- Fixing a symptom that's actually a model issue. HC#10 routes to `join-and-relationship-advisor` first.
- Chaining clarifiers past the first. HC#4 caps at one.
- Assuming multi-calc mode by default. HC#1 requires the clarifier.
- Treating an `author-calc` success response as proof only the intended calc changed. Per calc-writer anti-pattern: verify the returned name/formula match the fix request before delivery.
- Retrying `author-calc` after 2 hangs. Portfolio pattern says stop and hand off manually.
- Reporting `verified: true` when `sample_size` is below the 1,000-row reliability threshold. Report `sample_size: below_threshold` instead per the Row-Count Tiers table; never round up confidence to mask a small sample.

## Known Limitations

- Default mode is one calc per invocation; multi-calc requires HC#1 opt-in.
- Original broken calc left in place by default; user must opt in to overwrite.
- Parameter creation is out of scope (platform gap).
- Set and hierarchy creation are out of scope.
- Fresh-parameter resolution has documented one-retry pattern.
- Sample-size threshold requires ≥1,000 rows for verified.
- `author-calc` hang is non-deterministic per a known calc-writer finding; connection-type-independent. Fail-open + manual-handoff recovery is the correct discipline.
- Grain-related failures (E-GRAIN) may require routing to `join-and-relationship-advisor` before this skill can propose a calc-side fix.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. ## Performance Hierarchy (Locked, 5 Tiers)

Full catalog in `skill-expertise/performance_hierarchy.md`. Summary:

- **Tier 1 (fastest):** Boolean row-level, INT arithmetic, indexed field references, simple arithmetic on native measures.
- **Tier 2:** Aggregated arithmetic (`SUM(...) / SUM(...)`), single-dimension FIXED LOD, IF/ELSEIF on aggregates.
- **Tier 3:** Multi-dimension FIXED LOD, INCLUDE/EXCLUDE LOD, string equality checks.
- **Tier 4:** Nested LODs (depth 1), CONTAINS/STARTSWITH on non-aggregated strings, DATEDIFF in filter context, table calcs where a FIXED LOD would suffice.
- **Tier 5 (slowest):** COUNTD on high-cardinality fields, REGEXP_MATCH, nested LODs (depth 2+), row-level string ops inside aggregations, cross-datasource blending in calc context.

Every optimization delivery reports the tier movement: `optimization_tier_movement: {from: 4, to: 2}` or `optimization_tier_movement: none` for "already optimal."

## Phase Sequence

- **Phase 0.** Identify target data source. Multi-source ambiguity fires HC#4 clarifier with role/type disclosure.
- **Phase 1.** Read the original formula. Resolve every field reference via `list-available-fields`/`resolve-field`. Refuse silent substitution on missing fields (HC#5).
- **Phase 2.** Rank the original against the Performance Hierarchy. Note tier and specific slow-path flags (e.g., PA-COUNTD-HIGH-CARDINALITY, PA-REGEXP-IN-AGGREGATE).
- **Phase 3.** Generate rewrite candidates in decreasing-tier order (start from tier 1, work down). If original is already at tier 1 or is genuinely optimal at its tier, deliver "already optimal" verdict. Before keeping any candidate, look up every function it uses in `skill-expertise/INDEX.md` per HC#13.
- **Phase 4.** Filter candidates through the V-gate. Reject any candidate that itself violates a V-gate rule. Never ship a rewrite that fails its own gate.
- **Phase 5.** Author the surviving best candidate via `author-calc` as `[original name] Fast` (or overwrite the original only if user explicitly opted in per HC#12).
- **Phase 6.** Mandatory equivalence verification. Author both original and optimized on a scratch worksheet. Sample aggregated values by every dimension the original touches. Compare row-by-row. Fail-open on double failure per HC#8.
- **Phase 7.** Emit `calc_optimize_handoff/1` YAML unprompted with Performance Hierarchy movement, Trade-offs block, verification status.
- **Phase 8.** Clean up scratch worksheet.

## Validation Gate

Full spec in `skill-expertise/validation_gate.md`. 8-check gate identical to calc-writer/debugger:

- R-TYPE-01, R-TYPE-02: classification and return type match original.
- R-AGG-01, R-AGG-02: aggregation wrapping; ATTR two-condition rule.
- R-LOD-01, R-LOD-02, R-LOD-03: LOD syntax, nesting depth, filter order-of-operations.
- R-TC-01, R-TC-02: table-calc partitioning; prefer FIXED LOD.
- R-NULL-01: NULL handling explicit.
- R-BOOL-01: TRUE/FALSE/NULL, not 1/0/-1.
- R-PERF-01: no row-level string ops in aggregations.
- R-NAME-01: `[original name] Fast` default; ≤20 chars unless original was longer.

Plus one optimizer-specific check:

- **R-EQUIV-01:** optimized formula returns the same values as the original for every group the original produces. Verified via runtime equivalence check on scratch worksheet. Fail-open on double failure per HC#8.

## Verification Derivation-Prefix Rule

Resolve derivation prefixes from the calc's actual AGG-flag via `list-available-fields`/`resolve-field`, not by string-matching the formula for aggregation functions. A FIXED LOD pill placed on a shelf has AGG-flag `false` and gets `sum:` even though the formula string contains `SUM(...)`. String-matching would incorrectly force `usr:`.

## Domain-Accuracy Assertions (Locked)

These are directional rankings for typical extract-backed sources, not measured guarantees for every backend — see the Connection-Type Caveat in `skill-expertise/performance_hierarchy.md`. On live connections to pushdown-capable databases, the underlying engine's own optimizer can narrow these gaps.

- Boolean row-level calcs typically faster than aggregated boolean rewrites when the intent is a row-level flag.
- COUNTD is typically slower than SUM/AVG on the same field; the perf hit scales with cardinality.
- REGEXP_MATCH is typically slower than CONTAINS on the same string test; CONTAINS is typically slower than equality on an indexed field.
- FIXED LOD depth 1 is typically faster than FIXED LOD depth 2+; flatten wherever semantics allow.
- Filter-order-of-operations: FIXED executes before dimension filters (unless promoted to context); INCLUDE/EXCLUDE execute after. Optimizer must not silently change this relationship — this ordering rule is a fixed Tableau semantic, not a perf heuristic, and always holds regardless of connection type.
- Table calcs are typically slower than FIXED LODs that achieve the same semantics; rewrite to LOD wherever possible.
- Cross-datasource blending inside a calc is typically slower than reshaping the data model; if optimization would require this, route to `join-and-relationship-advisor`.

- `list-available-fields` — Phase 1 (verify all referenced fields exist; resolve AGG-flag for each). Default practice, not just the >100-field edge case: batch calls in groups of ~10 with inline progress notes whenever the workbooks field count makes a single call unwieldy.
- `resolve-field` — Phase 1 (resolve derivation prefix per fields actual AGG-flag; never string-match the formula).
- `author-calc` — Phase 5 (author the rewritten calc, only on user opt-in).
- `get-summary-data` — Phase 6 (mandatory R-EQUIV-01 verification: author original + rewrite on scratch worksheet, compare aggregated values). On a live (non-extract) datasource connection, this call is slower than on an extract; apply the high-cardinality sampling cap (top 200 + random 100) proactively rather than waiting for the >500-group threshold to be reached, to bound wait time.
- No file writes. Skill is compute-only; downstream consumers write.

## House-Style Catalog (Locked, 12 Rules)

Full catalog in `skill-expertise/style_catalog.md`. Summary:

**Naming (severity: error)**
- **S-NAME-01:** Calc name is ≤20 characters unless it inherits a longer parent name. A skill-added suffix (` Clean`, ` Fast`, ` Fixed`) doesn't count toward the 20.
- **S-NAME-02:** Calc name uses Title Case, no leading/trailing whitespace, no double spaces.
- **S-NAME-03:** Calc name is not a Tableau reserved word or a bare function name (e.g., SUM, COUNT).

**Structure (severity: warning)**
- **S-STRUCT-01:** IF/ELSEIF chains ≤4 branches; deeper chains flagged.
- **S-STRUCT-02:** Nested LODs deeper than depth 1 documented in a leading comment or flagged.
- **S-STRUCT-03:** Table calcs document partitioning/addressing in a leading comment or flagged.
- **S-STRUCT-04:** No unnecessary parentheses around single-token operands.

**Comments (severity: info)**
- **S-COMMENT-01:** Calcs longer than 5 lines have a leading comment explaining purpose.
- **S-COMMENT-02:** Non-obvious literal values (magic numbers, business thresholds) have inline explanatory comments.

**Formatting (severity: info)**
- **S-FORMAT-01:** Indentation uses spaces (2 or 4), consistent within one calc.
- **S-FORMAT-02:** No trailing whitespace on any line.
- **S-FORMAT-03:** One blank line max between logical sections.

Every violation is reported with its rule ID, severity, and one-line rationale. Rewrite suggestions render only when the violation is safely rewritable (see R-EQUIV-01 discipline below).

## Phase Sequence

- **Phase 0.** Identify target data source. Multi-source ambiguity fires HC#4 clarifier with role/type disclosure.
- **Phase 1.** Read the original formula. Resolve every field reference via `list-available-fields`/`resolve-field`. Refuse silent substitution on missing fields (HC#5). Re-verify any consumed handoff payloads references.
- **Phase 2.** Run the calc against the 12-rule catalog. Log every violation with severity + rationale.
- **Phase 3.** Assemble the lint report. Group violations by severity (error → warning → info). If zero violations, deliver clean verdict.
- **Phase 4.** If user opted in to rewrite (HC#11), generate rewrite candidates per violation. Filter through the V-gate. Reject any candidate that itself violates a V-gate rule or would change returned values. Before keeping any candidate, look up every function it uses in `skill-expertise/INDEX.md` per HC#13.
- **Phase 5.** Author the rewritten calc via `author-calc` as `[original name] Clean` (or overwrite the original only if user explicitly opted in per HC#12).
- **Phase 6.** Mandatory R-EQUIV-01 equivalence verification. Author both original and rewrite on a scratch worksheet. Sample aggregated values by every dimension the original touches. Compare row-by-row. Fail-open on double failure per HC#8.
- **Phase 7.** Emit `calc_lint_handoff/1` YAML unprompted with violations, rewrites (if any), and verification status.
- **Phase 8.** Clean up scratch worksheet.

## Validation Gate

Full spec in `skill-expertise/validation_gate.md`. 8-check gate identical to calc-writer/debugger/optimizer:

- R-TYPE-01, R-TYPE-02: classification and return type match original.
- R-AGG-01, R-AGG-02: aggregation wrapping; ATTR two-condition rule.
- R-LOD-01, R-LOD-02, R-LOD-03: LOD syntax, nesting depth, filter order-of-operations.
- R-TC-01, R-TC-02: table-calc partitioning; prefer FIXED LOD.
- R-NULL-01: NULL handling explicit.
- R-BOOL-01: TRUE/FALSE/NULL, not 1/0/-1.
- R-PERF-01: no row-level string ops in aggregations.
- R-NAME-01: `[original name] Clean` default; the original name part is ≤20 chars unless the original was longer. The ` Clean` suffix doesn't count.

Plus the optimizer-shared runtime check:

- **R-EQUIV-01:** any rewrite returns the same values as the original for every group. Verified via runtime equivalence check on scratch worksheet. Fail-open on double failure per HC#8. High-cardinality sampling cap (>500 groups → top 200 + random 100). Zero-dimension FIXED LOD read-gap recovery discipline preserved from calc-optimizer.

## Verification Derivation-Prefix Rule

Resolve derivation prefixes from the calcs actual AGG-flag via `list-available-fields`/`resolve-field`, not by string-matching the formula for aggregation functions. Preserves the runtime-lookup discipline confirmed in calc-writer/debugger/optimizer testing.

## Domain-Accuracy Assertions (Locked)

- IF/ELSEIF chain reordering can change short-circuit evaluation semantics. Never rewrite branch order without R-EQUIV-01 verification.
- IF-to-CASE conversion changes NULL propagation and equality semantics (CASE requires exact match; IF supports full comparison operators). Never do this rewrite unless the original formula is genuinely equality-only.
- Naming rewrites (S-NAME-*) never touch the formula body. Renaming is authoring a new calc with the new name, not editing.
- Comment additions never change formula semantics but can trigger `author-calc` reject if the comment syntax collides with formula syntax. Verify author-calc round-trip before delivery.
- Whitespace/indentation edits are semantically no-ops in Tableaus parser but must still pass R-EQUIV-01 as belt-and-braces.

## Scale-Tier Branching

For calcs with more than ~50 lines, batch the rule catalog into two passes: structural rules (S-STRUCT-*) first, then naming/formatting. For workbooks with more than ~100 fields (relevant when re-verifying handoff references), batch `list-available-fields` in groups of ~10 with inline progress notes.

## Multi-Calc Sequential Mode

Default: single calc per run. If user names multiple calcs, fire HC#1 clarifier: one at a time (default) or sequential this run? Sequential mode runs the full pipeline per calc, emits one `calc_lint_handoff/1` per calc, and ends with a session summary.

Failure isolation: if calc N fails a hard constraint (e.g., HC#5 missing field), calcs 1..N-1 and N+1..M still ship.

## Report Structure (Locked)

Every lint delivery renders this exact structure, even for clean verdicts:

- **Summary:** N violations found (X errors, Y warnings, Z info), or Clean — no violations.
- **Errors:** rule ID, rationale, snippet, rewrite suggestion (if safely rewritable). None surfaced is valid.
- **Warnings:** same shape.
- **Info:** same shape.
- **Rewrite delivered:** yes/no (only yes if user opted in AND R-EQUIV-01 passed).
- **Trade-offs (if rewrite delivered):** readability, maintainability, downstream impact. None surfaced is valid.

## Handoff Contract

Emits `calc_lint_handoff/1` unprompted after every delivery, including clean verdicts. Full schema in `skill-expertise/handoff_schema.md`. Required non-blank fields:

- `schema_version`, `datasource_name`, `original_calc_name`, `original_formula`
- `violations` (list; may be empty for clean verdicts)
- `rewritten` (true/false), `rewritten_calc_name` (only if `rewritten: true`), `rewritten_formula` (only if `rewritten: true`)
- `verified_equivalent` (true/false; N/A only if `rewritten: false`)
- `overwrites_original` (true/false)

## Refuse to Fabricate

Never invent a style rule outside the locked 12-rule catalog. Never fabricate a violation. Never silently rewrite. Never ship a rewrite that fails its own V-gate or R-EQUIV-01. Never invent a function signature (HC#13).

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

## Workflow Phases

- **Phase 0 Scope.** Confirm workbook is open via `get-workbook-inventory`. If zero calcs exist, exit cleanly per HC#7 with no calculated fields defined; hygiene scan not applicable.

Stale handoff forces local-extract fallback per HC#13; skill does not render against stale data.
- **Phase 2 Rule Evaluation (numbered checklist).**
  1. For each calc in the workbook, apply each of the 8 rules from `skill-expertise/rule_catalog.md`.
  2. Formula text for parse-depth (CH-NESTING-04) and pattern-match rules (CH-HARDCODED-05, CH-DEPRECATED-06, CH-LOD-OVERUSE-08) comes from `list-available-fields`s formula field when populated for a calc; if a given calcs entry has no formula text, treat that calc as formula-unreadable for those rules and emit the HC#5 sentinel for them specifically rather than assuming the tool always returns formula bodies.

## Hard Constraints

**HC#1 Read-only always.** Never mutates the workbook. Every finding is a manual Desktop-fix instruction plus (for autofixable rules) a routing signal to calc-linter.

- **Phase 0.** Identify target data source. Multi-source ambiguity fires HC#1 clarifier.

- **Phase 6.** Reconcile batched results into a single deduplicated inventory. Run the 3-check V-gate (all fields populated, batches reconciled, reference-graph consistent).

Full spec in `skill-expertise/validation_gate.md`. Every inventory passes:

- **V1 (Entry completeness):** every catalog entry has all required schema fields populated (or sentinel values per HC#8). No blanks. No fabricated fields.

## What it does

Takes one expression from another dialect and ports it to Tableau, one at a time. It parses the source, routes to the correct Tableau calc type (row-level, aggregate, LOD, or table calc), maps every function through a dialect-specific translation table, resolves every field reference against your target datasource, writes the calc, and verifies the output against real data on a scratch sheet.

Semantic drift is reported, not hidden. When a translation is approximate (DAX `EARLIER()` has no direct Tableau equivalent; Excel `IFERROR` catches errors that `IFNULL` doesn't; SQL integer division doesn't match Tableau's float division), Calc Translator gives you the closest expression AND an explicit caveat citing the drift catalog.

## When to use it

- "Translate this SQL to Tableau"
- "Convert this DAX to a Tableau calc"
- "Port this Excel formula to Tableau"
- "What would this Snowflake expression look like as a Tableau calc"

- Not for writing a Tableau calc from a natural-language description (use calc-writer)
- Not for debugging an existing Tableau calc (use calc-debugger)

- Not for setting up a data source connection (use data-source-connector)

**Never mutate the source system.** This skill translates *into* Tableau; it does not touch the origin SQL query, Excel workbook, or DAX model.

**One expression per run.** Multiple expressions run as separate Phase 0-6 cycles.

***

## Hard Constraints

1. **Verification is mandatory.** Every translated calc is verified via get-summary-data on a scratch worksheet. If verification is impossible (data source disconnected, sheet creation blocked, cloud timeout), state Unable to verify explicitly and refuse to declare the translation complete.

2. **Parameter-safe write path.** If the target data source contains any parameter-referencing calc (detected by scanning existing calc formulas for `[Parameters].` references), do not invoke `build-and-apply-worksheet` or `bind-template` with `auto_apply`. The corruption is silent and undetectable via formula readback. Use `add-worksheet` plus `add-field` only.

3. **Bare parameter names.** When a translation includes a parameter reference, the Tableau formula uses the bare parameter name, never `[Parameters].[X]`. Double-qualification breaks author-calc silently.

4. **20-character field name cap.** Every translated calc name is 20 characters or fewer. Propose a shortened name if source exceeds this; confirm with the tester before writing.

5. **Comment placement after formula.** author-calc collapses leading newlines. Translation comments go at the end of the formula, never at the top.

6. **Blocking-modal awareness.** If any tool call hangs, times out, or returns garbled results after a mutation, instruct the tester to check Tableau Studio for a modal dialog before continuing. Do not retry the call.

7. **Semantic drift is reported, not hidden.** When a translation is approximate (DAX `EARLIER()` has no direct Tableau equivalent; Excel `VLOOKUP` maps to a join), output both the closest Tableau expression and an explicit This is not an exact translation. Difference: X. caveat citing the Semantic Drift Catalog.

8. **No fabricated fields.** If a source-side field has no counterpart in the target Tableau data source, stop and ask the tester to map the field or provide the missing one. Never invent a field.

9. **Calc-type routing is deterministic.** The Tableau calc type is determined by pattern-matching the source expression against the Calc-Type Routing table, not by inference. Ties resolve to the tables rule, not the models judgment.

10. **Single-expression only.** If the tester pastes multiple expressions, ask which one to translate first and offer to re-run for the others. Do not batch.

11. **Calc Optimizer handoff is offered, never forced.** After a VERIFIED translation, offer the handoff to Calc Optimizer. Never auto-invoke. If the tester declines, close the run cleanly.

12. **Declined handoff is a valid completion state.** Not every translation needs optimization. If the tester says ship it as-is, the run is complete. Do not treat this as an incomplete or failed run.

***

## Common Mistakes

Scan before writing any calc:

- **Assuming SQL function argument order matches Tableau.** `DATEADD` in SQL Server is `(part, number, date)`; Tableau uses `(part, interval, date)` — similar order, different terminology. `DATEDIFF` returns a different signed value on certain boundaries. Always check the Translation Rules table.
- **Translating DAX `CALCULATE` naively.** CALCULATE with filter modifiers is not a Tableau row-level calc — it is an LOD. Route via the Calc-Type Routing table.
- **Translating Excel `VLOOKUP` as a Tableau calc.** VLOOKUP is a join, not a calc. Refuse translation and hand off to `join-and-relationship-advisor`.
- **Writing the calc before resolve-field confirms every reference.** author-calc will succeed and produce a broken calc if a field is unresolvable.
- **Skipping verification because the source expression looked simple.** Simple expressions are the most common source of silent semantic drift (rounding rules, null handling, integer vs. float division).
- **Preserving the source name verbatim when it exceeds 20 characters.** Propose a shortened name up front.
- **Applying the T: prefix in a way that produces a duplicate.** If `T: X` already exists, increment to `T: X v2`. Never overwrite.
- **Auto-invoking Calc Optimizer.** The handoff is offered, not forced. Skipping the offer is a valid choice.
- **Treating a declined Calc Optimizer handoff as a failed run.** If the tester says no thanks, ship as-is, the run is complete.
- **Burying a per-key predicate inside the aggregate.** When the logic is a per-key test (e.g. customers with 2+ orders), offer a standalone flag calc (`{ FIXED [key] : agg } >= n`, boolean dimension) alongside the aggregate rate. Testers often prefer the reusable flag. Warn that a plain SUM or COUNT over the flag counts rows, not keys; use COUNTD(IF flag THEN key END).

## Worked Example — DAX CALCULATE + FILTER

Demonstrates the highest-value routing decision this skill makes. Base agent without the skill would typically route this as a row-level calc and produce wrong output. The skill routes correctly to an LOD and verifies.

**Input from tester:**

> Translate this DAX to Tableau: CALCULATE(SUM(Sales[Amount]), FILTER(Sales, Sales[Region] = "West"))

**Without the skill (baseline agent behavior):**

The agent would likely produce something like `IF [Region] = "West" THEN SUM([Amount]) END` — which is a mixed-aggregation row-level calc, produces null in most contexts, and drops the dimensional filter context DAX implied. Silent semantic error.

**With the skill (Phase 0 → Phase 6):**

**Phase 0.** Tester confirms: DAX source, target data source is Sales_Extract (single connected DS, auto-selected). No parameter-referencing calcs detected. Standard write mode.

**Phase 1.** Parse and route.

> Parsing DAX. The expression uses CALCULATE with a FILTER modifier, which imposes dimensional filter context. Per the Calc-Type Routing table, this routes to an LOD, not a row-level calc.
>
> Fields referenced: Sales[Amount], Sales[Region]. Both must resolve on the target.
>
> Proposed routing: FIXED LOD on Region. Confirm before I resolve fields?

Tester: confirmed.

**Phase 2.** Batched resolve-field calls for Amount and Region. Both resolve. No parameters referenced.

**Phase 3.** Translate and write.

> Translation:
>
> ```
> { FIXED : SUM(IF [Region] = "West" THEN [Amount] END) }
> // Translated from DAX CALCULATE(SUM([Amount]), FILTER([Region] = "West")).
> ```
>
> Proposed name: `T: West Sales` (13 characters, under the 20-char cap).
>
> Pre-write validation:
> - No parameter double-qualification: PASS
> - Name length: PASS (13/20)
> - Comment position: PASS (at end)
> - No collision: PASS (no existing `T: West Sales`)
>
> Writing via author-calc now.

author-calc succeeds. Calc appears in list-available-fields.

**Phase 4.** Verify.

> Creating scratch worksheet `T-Verify-2026-09-01-1247`. Placing `Region` on Rows and `SUM([T: West Sales])` on Text.
>
> get-summary-data returns:
> - West: 145,230
> - Every other region: 145,230 (same value, because a table-scoped FIXED ignores the Region dimension in the view)
>
> Expected behavior for a table-scoped FIXED LOD with a West-only condition. VERIFIED.
>
> No drift caveat needed for this pattern — CALCULATE with a single equality filter maps cleanly to a FIXED LOD with a conditional aggregate.

**Phase 5.** Handoff offer.

> Translation is verified. This is an LOD. Want me to hand off to `calc-optimizer` for a performance optimization pass and deeper verification? (yes/no)

Tester: no thanks, ship as-is.

**Phase 6.** Deliver.

> Complete.
>
> - Source: `CALCULATE(SUM(Sales[Amount]), FILTER(Sales, Sales[Region] = "West"))`
> - Target: `T: West Sales` = `{ FIXED : SUM(IF [Region] = "West" THEN [Amount] END) }`
> - Calc type: LOD (FIXED)
> - Verification: VERIFIED
> - Drift caveats: none
> - Manual follow-ups: drop the `T:` prefix once you approve final placement
> - Handoff outcome: declined; shipped as-is
>
> Translate another expression?

**What the skill prevented:**

- Row-level routing (mixed-aggregation error)
- Missing dimensional filter context
- Silent verification (would have shipped without a get-summary-data check)
- Double-qualification if the source expression had referenced `[Parameters].[Region]` instead of a literal
- Name overflow if the source calc name had been `West Region Sales Aggregate`

## Workflow

### Phase 0 — Intake and Setup

**Batching:** issue list-workbook-datasources and list-available-fields in one turn.

1. Ask the tester:
   - Source dialect: SQL (which vendor), Excel, or DAX?
   - Paste the expression (single expression only).
   - Target data source in the workbook (if multiple exist).
2. Confirm the target: `list-workbook-datasources`. If multiple, ask which. If one, auto-select.
3. Check for parameter-referencing calcs on the target data source (scan formulas from `list-available-fields` for `[Parameters].` references). If present, enter parameter-safe mode (see Hard Constraint 2).
4. Call `get-workbook-inventory` alongside `list-available-fields` to check for a prior `T:`-prefixed calc from an earlier session before assuming the field list alone is sufficient for collision-checking in Phase 3.
5. If the testers stated dialect/vendor isnt one of the covered SQL vendors, Excel, or DAX, ask which vendor it is; if a function has no Translation Rules entry, follow the Source-side function has no Translation Rules entry row in Error Handling rather than guessing.

### Phase 1 — Parse and Route

1. Parse the source expression to identify:
   - Referenced fields (map to Tableau via `list-available-fields`)
   - Referenced parameters (flag for manual creation guidance)
   - Functions used (map via Translation Rules below)
   - Aggregation patterns (SUM, COUNT, DISTINCT, window functions)
   - Filter modifiers (WHERE, DAX CALCULATE modifiers, Excel IF wrappers)

2. Route to a Tableau calc type using the Calc-Type Routing table:
   - Row-level source function → Tableau row-level calc
   - Source aggregation without dimensional context → Tableau aggregate calc
   - Source aggregation with dimensional filter or partition context → Tableau LOD
   - Source window function → Tableau table calc
   - Source lookup across tables → flag as relationship, not calc; refuse translation

3. Announce the route to the tester with the reasoning (This is an LOD because the source uses a dimensional filter modifier). Give them a chance to override.

### Phase 2 — Resolve Fields

**Batching:** issue all resolve-field calls in one turn.

1. For every field named in the source expression, call `resolve-field`. If any field is unresolvable, stop and ask the tester to provide a mapping or add the missing field.

2. If a source parameter is referenced, do not attempt author-parameter. Generate a manual-creation instruction block for the tester and continue Phase 2 assuming the parameter will exist by verification time.

### Phase 3 — Translate and Write

1. Assemble the Tableau expression using the Function Mappings and the routed calc type.
2. Apply the 20-character name cap. Propose a name; confirm with the tester.
3. Place translation-note comments at the end of the formula (never the beginning).
4. **Pre-write validation gate (mandatory).** Before calling author-calc, read the drafted formula string back and confirm all four checks pass:
   - **No parameter double-qualification:** the string contains zero occurrences of `[Parameters].`. If found, strip to bare parameter name and re-check.
   - **Name length:** the proposed name is ≤ 20 characters. If over, stop and propose a shorter name.
   - **Comment position:** any translation comment appears after the final formula token (never before or interleaved). If comments are misplaced, move them to the end.
   - **No collision:** `T: {name}` does not already exist in list-available-fields output. If it does, increment to `T: {name} v2`.

   If any check fails and cannot be auto-corrected, stop and surface the specific failure to the tester. Never call author-calc while a check is failing — the writes are hard to reverse (no delete-calc tool).

5. Call `author-calc` with:
   - Name: `T: {shortened-name}`
   - Formula: translated expression, comments at end
   - Data source: confirmed target
6. Confirm the calc appears in `list-available-fields`. If not, the write failed silently — check for a blocking modal.

### Phase 4 — Verify

1. Create a scratch worksheet with a distinct name (e.g., `T-Verify-{timestamp}`). No delete-sheet or delete-calc tool path exists, so the scratch sheet and the authored calc persist. Tell the tester up front, naming the sheet, so they can remove it manually.
2. Place the translated calc via `add-field`. A row-level calc can go on Detail. An LOD calc can't go on Detail as-is: put the grouping dimension on Rows and the calc on Text as `SUM(...)` (or `ATTR(...)`). Add companion fields the verification needs. Run this step right after `author-calc`; don't wait for the user to ask.
3. Call `get-summary-data`. Compare against:
   - The testers expected value if provided
   - A hand-calculated value if the expression is simple enough to compute manually
   - The source systems output if the tester can paste it
4. Log the verification result: **VERIFIED**, **DRIFT** (plausible but different; report delta), or **UNVERIFIED**.
5. If drift is detected, cross-reference the Semantic Drift Catalog. Include the caveat text verbatim in output.
6. If the target data source returns fewer than ~5 rows, note in the delivery summary that verification confidence is lower — a small sample can mask a DRIFT that would only appear at scale.

### Phase 5 — Calc Optimizer Handoff (optional)

After VERIFIED, offer the handoff:

> Translation is verified. This is a {row-level / aggregate / LOD / table calc}. Want me to hand off to {calc-optimizer} for performance optimization and a deeper verification pass? (yes/no)

Route based on calc type:
- Any calc type (row-level, aggregate, LOD, or table calc) → `calc-optimizer`

**On yes:**
1. Invoke the sibling skill via the `Skill` tool, passing the translated calc name, the source-dialect context, and any drift caveats as input.
2. The sibling skill returns an optimized version (or confirms the translation is already optimal) plus a deeper verification report.
3. Confirm the tester wants to apply any sibling-proposed changes; if yes, the sibling handles the write. If no, the original translation stands.

**On no:** close the run cleanly. Log in the delivery summary: Handoff declined; translation shipped as-is.

Handoff is never forced. Declining is a valid completion state.

### Phase 6 — Deliver

Summarize in chat:
- Source expression (verbatim)
- Target Tableau calc name and formula
- Calc type chosen and why
- Verification status (VERIFIED / DRIFT / UNVERIFIED)
- Semantic-drift caveats if applicable
- Manual follow-ups (parameter creation, join setup, T: prefix cleanup)
- Handoff outcome (accepted / declined / not offered)

Offer to write a translation report to the testers Downloads folder if the translation was non-trivial. Offer to translate additional expressions one at a time.

## Composability

- **Upstream:** offered proactively after `data-source-connector` completes on a data source that is a known migration target (e.g., a Snowflake DS just connected while porting a Power BI dashboard).

### Calc-Type Routing (deterministic)

| Source pattern | Tableau calc type |
|---|---|
| Row-level function (LEN, LEFT, IIF, DATEADD without aggregation context) | Row-level calc |
| Aggregation with no dimensional context (SUM, AVG, COUNT) | Aggregate calc |
| Aggregation with dimensional filter/partition (CALCULATE with FILTER, SQL PARTITION BY, Excel SUMIF) | LOD (FIXED / INCLUDE / EXCLUDE per pattern) |
| Window function (ROW_NUMBER, RANK, LAG, LEAD, RANKX) | Table calc |
| Cross-table lookup (VLOOKUP, DAX RELATED, INDEX-MATCH) | Not a calc — relationship |

### Semantic Drift Catalog (top 6)

1. **SQL integer division vs. Tableau float division.** SQL `5 / 2` returns 2; Tableau returns 2.5. Caveat text: SQL performed integer division; the Tableau translation uses float division. Wrap in INT() if integer semantics are required.

2. **DAX context transition.** CALCULATE modifies filter context in ways with no exact Tableau equivalent. Caveat text: This DAX expression uses filter context transition, which has no exact Tableau equivalent. The LOD translation approximates the common case; verify against the source system for nested-filter scenarios.

3. **Excel error semantics vs. Tableau nulls.** IFERROR catches `#N/A`, `#DIV/0!`, `#VALUE!`, etc.; IFNULL catches only nulls. Caveat text: IFERROR catches all Excel error types; the Tableau IFNULL translation catches only null. If the source column contains non-null errors, add explicit type checks.

4. **Timezone handling.** SQL date functions may include timezone offsets Tableaus DATE type does not preserve. Caveat text: Timezone information may be lost in translation. If source data is UTC or timezone-aware, verify Tableaus DATE type behavior on your data.

5. **Rounding modes.** SQL and Excel typically use away-from-zero rounding; Tableau uses bankers (round-half-to-even). Caveat text: Tableaus ROUND uses bankers rounding (0.5 rounds to nearest even integer). Source SQL/Excel typically uses away-from-zero rounding. For financial or regulatory calculations, verify.

6. **FIXED LOD ignores dimension and date filters.** DAX evaluates variables and iterators under every filter on the page; a Tableau FIXED LOD ignores regular dimension and date filters. Caveat text: DAX respects every filter on the page, but a FIXED LOD in Tableau ignores regular dimension and date filters. If you filter to 2023, a customer's order count still spans all years, so a customer with one order in 2023 and one in 2021 counts as repeat in Tableau but not in DAX. To match DAX, right-click each filter and choose Add to Context (manual Desktop step; no tool sets context filters). INCLUDE is usually a poor substitute because it returns a per-view-level value and cannot be nested inside COUNTD(IF ... THEN key END) without mixing aggregate and row-level fields. State this caveat in Phase 4 and Phase 6 whenever a DAX or SQL translation routes to a FIXED LOD.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

# Calc Migrator — when to use

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/calc-family/calc-migrator

## What it does

Takes one calculated field, resolves every field reference against the target datasource, remaps them with your explicit approval per field, and writes a sibling copy on the target with a `_migrated` suffix. Every write is verified by re-reading the target calc so a manual paste with a typo never gets marked applied.

## When to use it

- "I duplicated a datasource and need to move my calcs to the new one."
- "I built a calc on dev and want to move it to prod without hand-editing every field."
- "I have a source and target that share field names and I need one calc ported cleanly."

## When NOT to use it

- Not for bulk-calc migration (not supported).
- Not for cross-workbook migration (out of scope).
- Not for rewriting calc semantics like aggregate-to-LOD (route to calc-optimizer).
- Not for authoring new calcs from scratch (route to calc-writer).
- Not for producing the before/after report (route to calc-migrator-diff-report after migration).

## How to trigger it

# Calc Migrator

Same-schema only (source and target must share referenced field names). Requires a fresh `calc_documentation/1` handoff from calc-documenter with formula-hash match. Read-only against the source calc; mutating only on the target datasource under explicit user go-ahead per field-rewrite. Trigger with migrate this calc, move calc to another datasource, calc-migrator, port this calc to another data source. Do NOT trigger on. bulk-calc migration (not supported), cross-workbook migration (out of scope), rewriting calc semantics like aggregate-to-LOD (route to calc-optimizer), authoring new calcs from scratch (route to calc-writer), explaining a calc (route to calc-explainer), diagnosing NULLs (route to calc-debugger), producing a before/after report (route to calc-migrator-diff-report post-migration).

## Purpose

Migrate a single Tableau calculated field from a source datasource to a target datasource inside the same open workbook. Read against the source; sibling-copy write on the target via `author-calc` with a `_migrated` suffix. Original source calc is never touched. Every field-reference rewrite requires user consent; the final composed formula requires an explicit go-ahead before `author-calc` fires. Same-schema only: source and target must share the names of every field the source calc references, or the migration is refused with a routing recommendation.

Consumes calc-documenter's `calc_documentation/1` handoff for the reference graph and aggregation classification; refuses to run without it.

## Trigger Conditions

## Do NOT Trigger On

- Bulk-calc migration across many calcs → not supported.
- Cross-workbook migration → out of scope; copy the calc manually.
- Rewriting calc semantics (aggregate → LOD, table-calc → LOD-fixed) → route to `calc-optimizer`.
- Authoring a new calc from scratch → route to `calc-writer`.
- Explaining what the source calc does → route to `calc-explainer`.
- Diagnosing why the migrated calc returns NULL → route to `calc-debugger`.
- Producing a before/after diff report → route to `calc-migrator-diff-report` after the migration completes.
- Cross-schema migration (target datasource lacks fields the source references with the same name) → refuse with a clean route to manual authoring.

## Scope Boundaries

- **IN.** One source calc + one target datasource + one migration per run. Same-schema only. Formula parse, field-reference resolution against target DS via `resolve-field`, aggregation reclassification against target DS schema, dependency remapping when the source calc references another calc that also exists on the target. Sibling-copy write via `author-calc` on the target DS with `_migrated` suffix. Per-field consent per rewrite. Final-formula go-ahead before `author-calc` fires. Handoff schema `calc_migration_report/1`.
- **OUT.** Any mutation of the source calc. Any datasource-model mutation on the target (new joins, relationships, field additions). Multi-calc, multi-workbook, multi-migration runs. Cross-schema field-name mapping. Semantic rewrites (aggregation type changes, LOD introduction, table-calc conversion). Bulk consent (per-field consent is HC#2).

**Same-schema rule.** The target datasource must contain every field the source calc references, with the same name. If the source calc references `[Sales]` and `[Category]`, both must resolve on the target via `resolve-field`. If any referenced field is unresolvable, migration is refused with `unresolved_references[]` populated and a manual-authoring route offered.

**Handoff consumption pattern.** Skill requires `calc_documentation/1` in session context with the target calc present in the handoffs calc list. If calc-documenter isn't installed, say so and offer two paths: (a) a read-only local extract of this one calc via `list-available-fields` and `resolve-field`, labeled `signal_source: local_extract`, with every consent step still required; or (b) the manual Desktop path: right-click the source calc > Copy, right-click the target data source > Paste, then fix any red field references. If missing, skill refuses with run calc-documenter first routing. If stale (V5 formula-hash mismatch), skill refuses with re-run calc-documenter routing. No local-extract fallback to protect the mutating write from stale-signal risk.

## Workflow Phases

- **Phase 0 Scope.** Confirm workbook is open via `get-workbook-inventory`. If `get-workbook-inventory` fails, times out, or returns empty for a workbook expected to be open, stop immediately and report the failure rather than proceeding on an unconfirmed workbook state. Ask user for source calc name if not stated. Resolve source calc via `resolve-field`. Ask user for target datasource. Confirm target datasource exists via `list-available-fields`.
- **Phase 0.5 Target Diff (mandatory, read-only, runs before offering any migration).** When the user names both datasources but not a specific calc, or names a calc without having seen the diff, compare the two datasources first. (1) List the calculated fields on the source datasource from `list-available-fields` (name, caption, formula). (2) For each, call `resolve-field` with the target `datasource` and record `missing_on_target` or `present_on_target`. (3) For each `present_on_target`, read the target formula from `list-available-fields` (or the cached workbook XML) and compare it to the source formula after whitespace normalization; record `identical` or `differs`. (4) Report in bullets: missing on target (migration candidates), present and differs (candidates only if the user wants to overwrite-by-sibling, `Migrated` suffix still applies), present and identical (nothing to do). (5) Note that `resolve-field` only looks up names taken from the source, so calcs that exist only on the target are not detected; say so rather than implying completeness. (6) Offer only the candidates from step 4, then continue to Phase 1 for the one calc the user picks. Never offer to migrate a calc that is present and identical. If the target datasource is not returned by `list-available-fields`, state that and use `resolve-field` with the target `datasource` name from `list-workbook-datasources` instead.
- **Phase 1 Handoff Check (mandatory).** Look for `calc_documentation/1` handoff in session context. If missing, refuse and route to calc-documenter. If present, verify the source calcs current formula hash matches the handoffs stored hash per V5. Mismatch = refuse and route to re-run calc-documenter. No local fallback.
- **Phase 2 Same-Schema Verification (numbered checklist).**
  1. Extract the field-reference list from the source calc formula via the handoffs `fields_referenced`. Exclude any field name that appears only as an LOD dimension declaration (between `{FIXED`/`{INCLUDE`/`{EXCLUDE` and `:`); those are deferred to Phase 3s LOD-dimension check and refusal routing, not this generic pass.
  2. Deduplicate the list; batch fields into groups of 20 for `resolve-field` calls per HC batching cap.
  3. For each referenced field, call `resolve-field` against the target datasource.
  4. Record each result in `resolution_log[]` as `resolved | unresolved`.
  5. If any field returns `unresolved`, populate `unresolved_references[]` with the exact field names.
  6. If `unresolved_references[]` is non-empty, abort migration with the missing-field refusal template from `skill-expertise/aggregation_preservation.md`.
  7. If all fields resolve, proceed to Phase 3.
- **Phase 3 Aggregation Preservation Check.** Classify the source calcs aggregation type per the locked decision tree in `skill-expertise/aggregation_preservation.md` (LOD-fixed → LOD-include → LOD-exclude → table-calc → aggregate → row-level). If the source is LOD-fixed, LOD-include, or LOD-exclude and the target DS lacks any of the LOD dimensions, refuse migration and route to calc-optimizer with the missing-LOD-dimension refusal template.
- **Phase 4 Per-Field Consent.** For each field reference in the source formula, present the user with the target-DS-resolved reference and ask for explicit confirmation. Track consent per field in `consent_log[]`. No batching; one field per prompt.
- **Phase 5 Compose Migrated Formula.** Assemble the final formula string using confirmed field references. Preserve author caption verbatim per HC#11. Assemble the target calc name as `{source_name} Migrated` (with a space, following Tableau naming conventions).
- **Phase 6 Final Go-Ahead.** Present the composed formula to the user with the proposed target calc name. Wait for explicit go-ahead. No implicit assent; user must state yes or equivalent to advance.
- **Phase 7 Sibling-Copy Write.** Invoke `author-calc` on the target datasource with the composed formula and `_migrated` naming. Verify write via read-back per calc-writers discipline. If `author-calc` fails or times out (non-deterministic hang), fall back to Desktop-manual instructions with the composed formula for the user to paste manually.
- **Phase 8 Validate.** Run the 5-check V-gate: schema coverage, handoff-hash match, per-field consent complete, final go-ahead recorded, sibling-copy discipline held (source untouched, target has new calc with `_migrated` suffix).
- **Phase 9 Deliver.** Compact single-tier chat output confirming migration status. Optional handoff to calc-migrator-diff-report for a before/after diff artifact.

## Hard Constraints

**HC#1 Source calc is read-only always.** Never invoke `author-calc`, `bind-template`, or any mutating tool against the source datasource. Source formula, source caption, source annotations, source references all remain byte-identical after the run.

**HC#2 Per-field consent required.** Every field-reference rewrite requires explicit user confirmation. No batching under one yes. User can approve fields one at a time or decline. Declined fields abort the migration with `unresolved_references[]` populated.

**HC#3 Final-formula go-ahead required.** The composed formula is presented in full before `author-calc` fires. No implicit assent. User states yes or equivalent to advance. Any other response aborts.

**HC#4 Refuse to fabricate.** No inferred field mappings. No guessed aggregation reclassification. No invented dependency remapping. If any resolution fails, abort with a manual-authoring route rather than proceed.

**HC#5 Handoff required upstream.** Migration cannot start without a fresh `calc_documentation/1` handoff (V5 formula-hash match). No local-extract fallback. This is stricter than calc-explainers opportunistic pattern because the write mutates state; stale signals are unacceptable.

**HC#6 Same-schema only.** If the target DS lacks any field the source calc references (by name), refuse with `unresolved_references[]` and route to manual authoring.

**HC#7 Aggregation preservation.** If the source calcs aggregation type cannot be preserved on the target (e.g., LOD-fixed dimensions missing), refuse with rationale and route to calc-optimizer for a semantic rewrite. Skill does not silently change aggregation type.

**HC#8 One calc, one target, one migration per run.** Multi-calc, multi-target, or multi-migration requests refused; not supported.

**HC#9 One workbook per run.** Cross-workbook migration refused; out of scope.

**HC#10 Sibling-copy discipline.** Target calc is always named `{source_name} Migrated` (with space per Tableau naming). Never overwrite an existing calc on the target DS. If a calc with that name already exists, append version suffix (`Migrated v2`, `Migrated v3`) per fresh-filename discipline.

**HC#11 Author caption preserved verbatim.** Source calcs caption (if present) is copied byte-identical to the target calc. Sources in-formula `//` annotations are copied byte-identical. Skill never rewrites, paraphrases, or removes author intent.

**HC#12 `author-calc` timeout fallback.** If `author-calc` hangs (documented non-deterministic hang) or fails, skill emits the composed formula in chat plus Desktop-manual paste instructions. Migration status marked `pending_manual_apply` rather than `applied`. Once the user reports the manual paste is done, skill re-reads the target calc via `list-available-fields` or `resolve-field` and confirms the formula matches the composed formula byte-for-byte before upgrading status to `applied` — a users done is not itself sufficient confirmation for a mutating write.

**HC#13 Never batch consent.** Even if the user says approve all field mappings, skill still presents each field individually. Per-field discipline is non-negotiable for a mutating skill.

**HC#14 Read-back verification.** After `author-calc` succeeds, skill reads the newly-created target calc and verifies the formula matches the composed formula byte-for-byte. Mismatch = migration marked failed, target calc flagged for user review.

**HC#15 Sentinel discipline.** Missing data uses `null`, `[]`, `unresolved: <raw>`, or `unknown`. Never fabricate to fill a schema field.

**HC#16 Wide-formula scale handling.** For source calcs referencing more than 15 unique fields, skill emits a wide-formula-notice in Phase 2 output (this calc references N fields; per-field consent will require N confirmations) and offers an opt-in bulk-review path: user reviews the full field-mapping table once, then confirms with a single confirm all mappings acknowledgment. Bulk-review still requires the user to have read the full mapping table (skill emits the table before requesting bulk confirmation). Bulk-review does NOT change HC#3 final-formula go-ahead requirements; that remains a separate explicit confirmation.

## Validation Gate (5-Check)

- **V1 Schema Coverage.** Every field the source calc references resolves on the target DS via `resolve-field`. `unresolved_references[]` empty.
- **V2 Handoff-Hash Match.** Source calcs current formula hash matches the handoffs stored hash. Staleness detected = abort.
- **V3 Per-Field Consent Complete.** `consent_log[]` shows explicit user approval for every field reference.
- **V4 Final Go-Ahead Recorded.** `final_goahead_timestamp` populated. No implicit or empty.
- **V5 Sibling-Copy Discipline.** Source calc byte-identical to pre-run state (verified by re-reading source formula). Target calc created with `_migrated` suffix. Read-back verified.

## Common Mistakes (Anti-Patterns)

- **Batching per-field consent under one yes.** Even if the user says approve all field mappings, skill iterates each field individually per HC#2 / HC#13. Bulk-review path per HC#16 is a separate opt-in mode for wide formulas and still requires the mapping table to be shown before the bulk acknowledgment.
- **Running without a fresh calc-documenter handoff.** HC#5 refuses this. No local-extract fallback. Mutating writes cannot survive stale reference-graph signals.
- **Silent aggregation swap.** Never reclassify a source LOD-fixed as an aggregate on the target because the outer SUM was seen first. Precedence Rule 1 in `skill-expertise/aggregation_preservation.md` blocks this.
- **Mutating the source calc.** HC#1 makes the source calc byte-identical before and after the run. Never touch it.
- **Skipping the final-formula go-ahead.** HC#3 requires explicit user yes on the composed formula. No implicit assent from any prior consent.
- **Overwriting an existing target calc.** HC#10 fresh-filename discipline appends `Migrated v2`, `Migrated v3` on collision. Never overwrite.
- **Fabricating field mappings.** If any field on the source calc fails to resolve on the target datasource, refuse the migration per HC#4. Do not guess a similar-named field.
- **Ignoring `author-calc` timeout.** HC#12 fallback lands to Desktop-manual paste with `pending_manual_apply` status. Never silently mark a hung migration as successful.

## Known Limitations

- **Same-schema only.** Cross-schema (target lacks sources field names) refused.
- **`author-calc` reliability gap**. Non-deterministic hangs; HC#12 fallback lands to Desktop-manual paste when the hang fires.
- **`resolve-field` case-sensitive** (platform gap). Field names must match exactly.
- **Cross-datasource field references** in the source calc are named but not resolved on the target if the sources cross-DS target isnt loaded. Skill refuses in that case per HC#4.
- **No aggregation semantic changes.** LOD-fixed source that cant preserve dimensions on target = refusal, not silent rewrite.
- **Cycle detection unbuildable via native authoring** (platform limitation). If the target DS already has a calc that references the migrated calcs name (rare, only via a pre-existing naming collision), fresh-filename discipline in HC#10 handles the collision, not cycle detection.
- **Parameter references in source calc.** If the source references a parameter, the target must have the same parameter by name. Fresh-parameter-resolution failure applies here; skill flags rather than fabricates.
- **`author-calc` cannot resolve a freshly-created parameter** (confirmed 2026-08-31). If migration composes a formula that references a parameter created earlier in the same session, author-calc may fail; HC#12 fallback lands to manual paste.
- **`author-calc` session-stale write failures independent of read path** (confirmed 2026-09-17 during calc-migrator-diff-report behavioral testing). Observed repeatedly: `author-calc` fails with a stale-Desktop-session error while `resolve-field` succeeds against the same session moments before and after. This is a write-path-specific reliability gap, not a general connectivity loss — do not assume the whole session is down just because a write fails; re-verify with a read call before concluding disconnection, and land on the HC#12 manual-paste fallback rather than repeatedly retrying the write.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

Every diff finding cites a `finding_type`. Multi-type findings tier by highest severity. Full detection criteria, evidence patterns, and worked examples in `skill-expertise/diff_catalog.md`.

| # | Finding Type | ID | Severity | Signal source | Downstream routing |
|---|---|---|---|---|---|
| 1 | Clean migration (formula changed, all fields remapped, validated) | DIFF-CLEAN-01 | Info | handoff + re-validation | None (no action needed) |
| 2 | Field-remap applied | DIFF-REMAP-02 | Info | handoff `field_remaps[]` | None (informational) |
| 3 | Sentinel emitted by calc-migrator (unresolved field, unresolvable calc) | DIFF-SENTINEL-03 | Warning | handoff `sentinels[]` | calc-writer (manual authoring) |
| 4 | Validation failure post-migration (target formula fails syntax or type check) | DIFF-VALIDATION-04 | Warning | handoff `validation_status` + re-validation | calc-debugger (NULL / error diagnosis) |
| 5 | Staleness detected (source workbook state changed since migration ran) | DIFF-STALE-05 | Warning | V5 formula-hash mismatch per calc, workbook-fingerprint mismatch | calc-migrator (re-run) |
| 6 | Unmigrated calc (in source but not in migration report) | DIFF-UNMIGRATED-06 | Warning | source-DS calc list vs. handoff `migrated_calcs[]` | calc-migrator (re-run with wider scope) |
| 7 | Formula-identical migration (target formula byte-identical to source; no remap needed) | DIFF-IDENTICAL-07 | Info | handoff formula comparison | None (informational; may indicate no-op migration) |

Deterministic sort per HC#10: severity tier (Warning → Info) → finding ID ascending → calc name alphabetical.

**Fallback discipline (HC#5).** When diff detection depends on data thats unavailable per calc (handoff missing formula body, re-validation tool call fails), skill emits `unable to determine` sentinel per HC#5 for that specific finding type on that specific calc. Other finding types on the same calc still evaluate.

## Workflow Phases

- **Phase 0 Scope.** Confirm `calc_migration_report/1` handoff is available in session context. If missing, stop and tell the user to run `calc-migrator` first — do not proceed to Phase 1 on a missing handoff. Confirm workbook is open via `get-workbook-inventory`; if the call fails, returns no workbook, or the session is disconnected, stop and tell the user to confirm Tableau Studio is open with a workbook loaded. Ensure one migration run per invocation per HC#2.
- **Phase 1 Handoff Verification.** Verify `calc_migration_report/1` handoff completeness. Field mapping from calc-migrator's `calc_migration_report/1`: `source_datasource` = `source.datasource`; `target_datasource` = `target.datasource`; the single migrated calc is `migrated_calcs[0]` with `source_formula` = `source.formula`, `target_formula` = `target.formula`, `field_remaps[]` = `consent_log[]`, `sentinels[]` = `unresolved_references[]`, `validation_status` = `status` plus `v_gate`. Apply this mapping before checking completeness. Required fields: `source_datasource`, `target_datasource`, `migrated_calcs[]` with per-calc `source_formula`, `target_formula`, `field_remaps[]`, `sentinels[]`, `validation_status`. If any required field is missing on the handoff itself, treat the run as incomplete and emit `handoff_incomplete: true` in output metadata; skill can still render diff for the calcs that do have complete data, but flags the handoff as partial. Populate workbook-fingerprint from `get-workbook-inventory` for HC#15 comparison in Phase 2. **Single-fetch discipline:** `get-workbook-inventory` is called once in Phase 1; its result (workbook fingerprint and inventory snapshot) is cached and reused for both the Phase 1 completeness check and the Phase 2 staleness re-validation — never re-fetched mid-run.
- **Phase 2 Re-Validation (numbered checklist).**
  1. For each calc in `migrated_calcs[]`, verify V5 formula-hash on the target formula against current workbook state. `formula-hash` and `workbook fingerprint` are values computed by this skill (a hash of the formula text and a hash of overall workbook state), not native Tableau APIs or Tableau-exposed properties — they exist purely for this skills own staleness bookkeeping. If the target formulas formula-hash from the handoff does not match the current workbooks formula-hash for that calc name on the target datasource, mark the calc `stale: true` and fire DIFF-STALE-05.
  2. Verify workbook fingerprint from the handoff matches current workbook fingerprint per HC#15. If mismatch, mark the whole run `run_stale: true`; per-calc staleness still evaluated individually via step 1.
  3. Re-validate every calcs target formula against the target datasource. Batch `resolve-field` calls in groups of 20 per portfolio-wide HC batching cap (matches calc-migrators Phase 2 pattern). If a batch call fails outright (timeout, disconnect), retry that batch once; on a second failure, emit `unable to determine` sentinel for every calc dependent on that batchs resolution and continue with remaining batches — do not abort the whole diff.
  4. For each calc, apply the 7 finding types from `skill-expertise/diff_catalog.md`. Populate `findings_triggered[]` with the finding ID, evidence citation, and `signal_source`.
  5. Enumerate source-DS calc list via `list-available-fields` and compare to handoff `migrated_calcs[]`. Any source calc not in the handoff fires DIFF-UNMIGRATED-06.
  6. For findings with unresolvable signals, emit `unable to determine` sentinel per HC#5 rather than skipping.
- **Phase 3 Severity Tiering + Deterministic Sort.** Sort per HC#10: severity tier (Warning → Info) → finding ID ascending → calc name alphabetical. Warning-tier findings surface in Tier A top 5.
- **Phase 4 Validate.** Run the 5-check V-gate: finding coverage, per-calc signal-source attribution, ordering determinism, handoff completeness, downstream routing correctness. If any check fails, do not discard the run: re-run only the failing checks underlying data pull once (e.g., re-fetch signal-source labels for V2, re-sort for V3), then re-validate that check. If it fails a second time, deliver Tier A with the specific V-check named as unresolved and the affected calcs/findings listed, rather than blocking delivery entirely or silently passing.
- **Phase 5 Deliver.** Two-tier: compact Tier A chat summary with counts and top 5 Warning-tier findings (staleness, validation failures, sentinels, unmigrated calcs); opt-in Tier B file save requires user path confirmation per HC#11.

## Hard Constraints

**HC#1 Read-only always.** Never mutates the workbook. Never invokes calc-migrator to re-run. Every finding is a diagnostic; downstream routing signals emitted but skill never chains invocation.

**HC#2 One migration run per invocation.** Multi-migration-run comparison refused.

**HC#3 7-finding-type catalog locked.** No finding type omitted, no fabricated finding type added. Detection follows the criteria in `skill-expertise/diff_catalog.md`.

**HC#4 Refuse to fabricate.** No inferred field remaps, no guessed migration rationale, no invented validation results. Sentinels: `null`, `unable to determine`, empty-state prose.

**HC#5 Sentinel discipline per finding per calc.** When a findings detection fails on a specific calc (handoff missing formula body, re-validation tool call fails for that calc), emit `unable to determine` sentinel for that finding on that calc. Other findings on the same calc still evaluate; other calcs still get all 7 finding types.

**HC#6 Handoff data quoted verbatim.** Source formula, target formula, field remaps, and sentinels from calc-migrators handoff are quoted byte-identical. Skill supplements around handoff data; never rewrites or paraphrases the migration output.

**HC#7 Sentinel discipline for zero-calc migration.** If handoff `migrated_calcs[]` is empty, exit cleanly with no calcs migrated in this run; diff report not applicable. Zero-calc source datasource also exits cleanly.

**HC#8 Diff-mode transparency** (portfolio-wide HC#13). Repeat invocations against unchanged handoff state emit `diff_mode: reused_verbatim` in Tier A. Fresh-scan / reused-verbatim / targeted-rescan enum. Note: `diff_mode` here refers to the diff-reports own idempotency, not to the migration diff content itself — the report is always presenting migration-diff content, but `diff_mode` tracks whether this specific report invocation is a fresh render or a re-render of unchanged inputs.

**HC#9 Ordering determinism** (portfolio-wide HC#14). Sort key locked: severity tier → finding ID → calc name alphabetical. Same input produces byte-identical top-5 and full findings list across runs.

**HC#10 Handoff-or-revalidation labeled per finding.** Every finding records `signal_source: handoff | revalidation | handoff+revalidation | unresolved` so downstream consumers know evidence origin. `handoff` = pure handoff data (e.g., field remap surfacing); `revalidation` = current-state re-check (e.g., staleness detection); `handoff+revalidation` = combines both (e.g., validation failure confirmed against current state).

**HC#11 Never silent file write.** Tier B save requires user path confirmation AND format choice (`.md` or `.txt`). No default writes to Downloads.

**HC#12 Downstream routing signals, never routing invocation.** For each Warning-tier finding, emit routing signals: DIFF-SENTINEL-03 → `routing.calc_writer: true`, DIFF-VALIDATION-04 → `routing.calc_debugger: true`, DIFF-STALE-05 and DIFF-UNMIGRATED-06 → `routing.calc_migrator: true`. Skill never invokes downstream skills directly per HC#1; user opts in.

**HC#13 Handoff staleness detection required** (portfolio-wide HC#15). V5 formula-hash check per calc when consuming calc-migration handoff. Per-calc mismatch fires DIFF-STALE-05 for that specific calc; other calcs with fresh hash-match still render normally. Workbook-fingerprint check per HC#15 fires run-level staleness.

**HC#14 Reference-file grounding.** All 7 finding types cite detection criteria and worked examples in `skill-expertise/diff_catalog.md`. Threshold defenses (V5 formula-hash discipline, validation-status semantics from calc-migrator, source-vs-target formula comparison rules) all documented with cross-references to calc-migrators contract.

**HC#15 Wide-workbook / bulk-migration scale handling.** For migration runs with 50+ calcs, skill emits a bulk-migration-notice in Tier A (this migration touched N calcs; Tier A truncates to top 5 per severity tier, full findings list in Tier B). Per-calc evaluation still runs on every calc; only presentation truncates. Warning-tier findings always surface fully in Tier A even beyond 5 if all are Warning; only Info-tier truncates. Per-calc evaluation cost scales linearly with calc count — there is no upper bound on migration size beyond the resolve-field groups-of-20 batching cap in Phase 2 step 3; a 200-calc migration runs the same per-calc logic as a 5-calc one, just in more batches.

**HC#16 Handoff completeness check.** Required fields on `calc_migration_report/1`: `source_datasource`, `target_datasource`, `migrated_calcs[]` (each with `source_formula`, `target_formula`, `field_remaps[]`, `sentinels[]`, `validation_status`). If handoff is missing any required field on the run-level, refuse with a route to re-run calc-migrator. If handoff is present but a specific calcs fields are incomplete, emit sentinels for those calcs per HC#5 and continue rendering the others. `resolve-field` case-sensitivity concern (a known platform gap, shared with calc-family): re-validation uses exact-case matches per HC#5 fallback.

## Validation Gate (5-Check)

- **V1 Finding Coverage.** All 7 finding types evaluated against every migrated calc plus any unmigrated source calcs.
- **V2 Signal-Source Attribution.** Every finding has `signal_source` populated per HC#10.
- **V3 Ordering Determinism.** Findings sort key deterministic per HC#9.
- **V4 Handoff Completeness.** `handoff_verified`, `handoff_incomplete`, `run_stale`, and per-calc `stale` flags all populated. Workbook-fingerprint match verified.
- **V5 Downstream Routing Correctness.** Every Warning-tier finding has the correct `routing.*` flag set per HC#12 (SENTINEL-03 → calc_writer, VALIDATION-04 → calc_debugger, STALE-05 / UNMIGRATED-06 → calc_migrator).

## Handoff Schema

Emits `calc_migration_diff/1`. Downstream: `calc-migrator` (re-run for STALE-05 / UNMIGRATED-06), `calc-writer` (manual authoring for SENTINEL-03), `calc-debugger` (NULL / error diagnosis for VALIDATION-04), `workbook-auditor` (migration-diff delta tracking).

## Common Mistakes (Anti-Patterns)

- **Auto-invoking calc-migrator to re-run.** HC#1 read-only + HC#12 routing-only. Skill emits `routing.calc_migrator: true` on STALE-05 / UNMIGRATED-06; user opts in.
- **Silent stale-handoff rendering.** HC#13 requires per-calc V5 formula-hash check plus run-level workbook-fingerprint check. Stale-per-calc fires DIFF-STALE-05; stale-per-run marks the whole run.
- **Rewriting handoff data.** HC#6 quotes source/target formulas verbatim. Skill supplements around them; never paraphrases.
- **Fabricating field remaps.** HC#4. DIFF-REMAP-02 evidence comes from handoff `field_remaps[]`; no inferred remaps.
- **Missing DIFF-UNMIGRATED-06 coverage.** HC#3 + V1 require enumerating source-DS calc list and comparing to handoff `migrated_calcs[]`. Source calcs absent from handoff fire this finding.
- **Silent file write on Tier B save.** HC#11 requires path confirmation AND format choice (`.md` or `.txt`).
- **Skipping a finding on a specific calc.** HC#5 requires all 7 finding types evaluated per calc (where applicable), with sentinel for unresolvable signals.
- **Confusing diff-mode enum with diff content.** HC#8 clarifies: `diff_mode` tracks this skills own idempotency across re-invocations; the migration-diff content itself is always the same 7-finding-type report.

## Adjacent-Skill Routing

- **Upstream required:** `calc-migrator` (produces `calc_migration_report/1` handoff).
- **Downstream opt-in per finding:**
  - DIFF-SENTINEL-03 → `calc-writer` (manual authoring for calcs calc-migrator couldnt resolve).
  - DIFF-VALIDATION-04 → `calc-debugger` (NULL / error diagnosis for target formula that fails validation).
  - DIFF-STALE-05 → `calc-migrator` (re-run because workbook state changed since migration).
  - DIFF-UNMIGRATED-06 → `calc-migrator` (re-run with wider scope to catch missed source calcs).
- **Downstream general:** `workbook-auditor` for migration-diff delta across runs.
- **Refusal routes:** running migration → `calc-migrator`; hygiene audit → `calc-hygiene-scan`; rewriting migrated calcs → `calc-writer` / `calc-optimizer`; NULL diagnosis → `calc-debugger`; workbook-level summary → `workbook-summary-onepager`; single-calc explanation → `calc-explainer`; full documentation → `calc-documenter`.

## Known Limitations

- Supports `.md` and `.txt` only.
- **DIFF-VALIDATION-04 depends on calc-migrators `validation_status` field being populated.** If calc-migrator emitted the field but with a coarse-grained value (e.g., `passed` / `failed` without per-check breakdown), diff-report inherits that granularity and cannot decompose further.
- **DIFF-UNMIGRATED-06 relies on complete source-DS calc enumeration via `list-available-fields`.** If that tool returns incomplete calc lists on a specific datasource, DIFF-UNMIGRATED-06 may miss calcs that should have fired it. HC#5 sentinel discipline applies.
- **`resolve-field` case-sensitivity concern**. Re-validation uses handoff data preferentially; local-extract fallback exact-case matches per rule.
- **Bulk-migration Tier A cap at top 5 per severity may hide Info-tier detail.** By design: Warning-tier always surfaces fully; Info-tier truncates. Full Info detail in Tier B.

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.

Source: https://tableau.github.io/tableau-ai-utilities/tableau-studio-skills/tableau-agent/calc-family/calc-documenter

## What it does

Scans every calculated field in an open Tableau workbook and produces a five-dimension dictionary entry per calc: formula (verbatim), fields referenced, reference graph (uses and used-by), sheet / dashboard usage, and aggregation context (row-level, aggregate, LOD-fixed, LOD-include, LOD-exclude, or table-calc). Author captions and in-formula `//` comments are preserved verbatim. Read-only. Nothing gets written back to the workbook. Chat delivers a compact summary; the full dictionary saves to a file only if you confirm the path.

## When to use it

- "I inherited a workbook with 40 calcs and I need to understand what's there before I touch it"
- "I need to hand this workbook off and want a proper calc dictionary as part of the handoff"
- "I want to see the reference graph so I know which calcs get consumed by other calcs vs. dead ends"
- "I need to run this before calc-explainer or calc-linter so the downstream skills have a handoff to consume"
- "I want to catch circular calc references or unused calcs during a governance sweep"

## When NOT to use it

- Not for explaining a single calc in plain language (use `calc-explainer`)
- Not for diagnosing why a calc returns NULL (use `calc-debugger`)
- Not for calc naming, hygiene, or comment audit (use `calc-linter`)
- Not for calc performance rewrites (use `calc-optimizer`)
- Not for authoring new calcs (use `calc-writer`)
- Not for cross-workbook or multi-workbook bulk runs (one workbook per invocation)

## How to trigger it

- "document all calcs in this workbook"
- "generate a calc dictionary"
- "calc-documenter"
- "produce a calc reference for this workbook"
- "build a dependency graph of the calcs"

# Calc Documenter

## When to use (full trigger detail)

Generate structural documentation for every calculated field in a Tableau workbook. Emits a per-calc dictionary with formula, fields referenced, reference graph (uses / used-by), sheets and dashboards using the calc, inferred aggregation level (row-level / aggregate / LOD fixed-include-exclude), and any existing author caption preserved verbatim. Read-only. Trigger with document my calcs, generate calc docs, calc dictionary, reference graph for calcs, calc-documenter, which calcs do I have, map my calc dependencies. Do NOT trigger on. single-calc explanation (defer to calc-explainer), calc syntax debugging (defer to calc-debugger), calc-family hygiene or naming audit (defer to calc-linter), applying documentation changes to calc captions (this skill is read-only), performance optimization (defer to calc-optimizer), workbook change-over-time (defer to workbook-auditor).

## Purpose

Generate structural documentation for every calculated field in a Tableau workbook. Emits a per-calc dictionary sorted by dependency order (or alphabetical fallback) with formula, referenced fields, reference graph, sheet/dashboard usage, inferred aggregation context, and preserved author captions. Read-only. Every entry cites XML evidence; no fabrication.

Positioned parallel to calc-inventory in the calc-family pipeline. Calc-inventory discovers what calcs exist; calc-documenter documents what each one is, does, and connects to. Downstream skills (calc-explainer, workbook-auditor, publish-readiness) consume the handoff.

## Trigger Conditions

- document my calcs
- generate calc docs
- calc dictionary
- reference graph for calcs
- calc-documenter
- which calcs do I have
- map my calc dependencies
- who uses this calc

## Do NOT Trigger On

- Single-calc natural-language explanation (defer to `calc-explainer`).
- Calc syntax debugging or NULL diagnosis (defer to `calc-debugger`).
- Calc-family hygiene, naming, or commenting audit (defer to `calc-linter`).
- Rewriting or applying documentation changes (all fixes are Desktop-manual per HC#1).
- Performance optimization (defer to `calc-optimizer`).
- Change-over-time (defer to `workbook-auditor`).
- Data-quality issues (defer to `data-quality-review`).
- Chart-type advisory (defer to `chart-swap-advisor`).
- Format-string drift (defer to `format-drift-scanner`).

## Scope Boundaries

- **IN.** One workbook per run. Every calculated field across every datasource in the workbook. Formula extracted verbatim from XML. Fields referenced (measures, dimensions, parameters, other calcs) parsed from formula and cross-referenced against `list-available-fields`. Reference graph (uses / used-by) constructed across the calc family. Sheets and dashboards pinning each calc to a shelf. Inferred aggregation context (row-level, aggregate, LOD fixed-include-exclude). Author captions preserved verbatim. Read-only. Handoff schema `calc_documentation/1`.
- **OUT.** Any workbook mutation. Applying doc changes to calc captions. Explaining a specific calc in plain language (calc-explainer). Naming or hygiene audit (calc-linter). Performance analysis. Multi-workbook runs.

**Cross-datasource workbooks.** Each datasources calcs documented in its own section. Cross-datasource references (calc in DS-A referring to a field in DS-B) flagged in the doc entry as `cross_datasource_reference`.

## The 5-Dimension Documentation Model

Every calc gets these five documentation dimensions:

| Dimension | Source | Verbatim? |
|---|---|---|
| Formula | `list-available-fields` `formula` attribute, with internal `Calculation_NNNN...` field-name tokens swapped for their resolved caption/name (see HC#16) | Yes, modulo caption substitution |
| Fields referenced | Parsed from formula, resolved via `resolve-field` | List, deduplicated |
| Reference graph | Cross-computed from every calcs Fields Referenced list | Directed (uses → used-by) |
| Sheet/dashboard usage | `get-worksheet-xml` shelves + `get-dashboard-xml` filters/parameters | List by name |
| Aggregation context | Inferred from formula (SUM/AVG/COUNT → aggregate; FIXED/INCLUDE/EXCLUDE → LOD-typed; no aggregate → row-level) | Enum |
| Author caption | XML `caption` attribute or worksheet-scoped description | Preserved verbatim |

**Sixth dimension (optional).** If a `<comment>` or annotation exists in the XML attached to the calc, include as `author_annotation`. Rare in most workbooks.

## Workflow Phases

- **Phase 0 Scope.** Confirm workbook is open via `get-workbook-inventory`. Enumerate datasources via `list-workbook-datasources`. For each datasource, enumerate calcs via `list-available-fields` filtered to calc-type fields. Ask user to scope only if total calc count exceeds 100 (default: all).
- **Phase 1 Extract.** For each calc: read formula, caption, aggregation attribute from XML. Parse formula for field references. Resolve each reference via `resolve-field` (batched per HC#5). Extract sheet/dashboard usage via `get-worksheet-xml` and `get-dashboard-xml`.
- **Phase 2 Build Reference Graph.** For every pair of calcs (A, B), if As formula references B, record A → B (uses) and B → A (used-by). Detect cycles; flag any circular dependency as `CD-CYCLE-01`.
- **Phase 3 Infer Aggregation Context.** For each calc, classify as row-level, aggregate, or LOD-fixed/LOD-include/LOD-exclude via formula pattern match. Cite the pattern that fired the classification.
- **Phase 4 Assemble Dictionary.** Sort calcs by dependency order (least-referenced first), fall back to alphabetical on ties. Group by datasource. Emit per-calc entries per `skill-expertise/documentation_template.md`.
- **Phase 5 Deliver Tier A.** Compact chat summary: total calc count, dependency-graph shape (linear, tree, DAG, cyclic), top 3 most-referenced calcs, save-file offer.
- **Phase 6 Deliver Tier B (opt-in).** Full dictionary written to Downloads as `.md` (default) or `.txt` only after user confirms path.

## Hard Constraints

**HC#1 Read-only always.** Never invoke `author-calc`, `bind-template`, `build-and-apply-worksheet`, or any mutating tool. Documentation is emitted; nothing is written back to the workbook.

**HC#2 One workbook per run.** Multi-workbook doc runs refused. Users invoke separately.

**HC#3 Bulk-action refusal.** Document all calcs and apply captions refused; skill is read-only per HC#1.

**HC#4 Locked five-dimension model.** Every calc entry includes formula, fields referenced, reference graph position, sheet/dashboard usage, aggregation context, and (if present) author caption. No dimension omitted. No fabricated dimension added.

**HC#5 Batching cap.** `resolve-field` batches capped at 20 per parallel call; `get-worksheet-xml` batches capped at 10 sheets per parallel call. Sequence remaining sheets in additional batches.

**HC#6 Never auto-invoke another skill.** Adjacent-skill routing (calc-explainer for natural-language explanation, calc-linter for hygiene) is an opt-in handoff.

**HC#7 Sentinel discipline.** Use `null`, `[]`, `unresolved` for missing XML fields. Never blank fields in the handoff schema. Field references that cannot be resolved via `resolve-field` render as `unresolved: <raw_reference>` in the doc entry.

**HC#8 Refuse to fabricate.** V-gate refuses fabricated field references, invented aggregation classifications, or missing formula citations.

**HC#9 Partial-info handling.** If `list-available-fields` returns partial results (per a known reliability gap), flag `PARTIAL-EXTRACT` for that datasource with reason; do not proceed with incomplete evidence.

**HC#10 Adjacent-skill routing.** Natural-language explanation → `calc-explainer`. Hygiene audit → `calc-linter`. Debugging → `calc-debugger`. Optimization → `calc-optimizer`.

**HC#11 Author caption preserved verbatim.** If the calc has an existing caption, description, or annotation in XML, include it in the entry as `author_description` or `author_annotation` verbatim. Never rewrite, paraphrase, or omit. Author intent is preserved even if it conflicts with the skills structural doc.

**HC#12 Never write the longform file silently.** File-save requires explicit user opt-in with path confirmation. Full dictionary lives in the file only; chat renders summary + top 3 only.

**HC#13 Guide the user actively.** Silence during evaluation is a defect. Announce progress on 50+ calc runs (per-datasource progress markers).

**HC#14 Cycle detection required.** Reference-graph construction detects and flags circular dependencies as `CD-CYCLE-01`. Never rendered as a valid dependency graph; cycles are flagged and the affected calcs marked `in_cycle: true`.

**HC#15 Ordering locked.** Dictionary entries render in dependency order (topological sort, least-referenced first). Alphabetical on ties. Within-datasource sort only; datasources render in `list-workbook-datasources` enumeration order.

**HC#16 Formula display must use resolved captions, not internal field IDs.** `list-available-fields` returns raw formula text containing internal tokens like `[Calculation_0831103151444568]` wherever the formula references another calc by its underlying column name rather than its caption. Before rendering a Formula line, every such token MUST be substituted with the referenced calc's resolved caption/name (e.g. `[Calculation_0831103151444568]` → `[Days to Ship Actual]`), using the same `resolve-field` lookups already performed for Fields Referenced in Phase 1. If a token cannot be resolved, leave it as the raw internal ID and flag it `"unresolved: <raw_token>"` per HC#7 — never silently display an unresolved internal ID as if it were final. When substitution occurs, append one line directly under the Formula block: `(stored internally as [<raw_token>, ...]; captions shown above)` so the reader knows the formula was translated, not misquoted. This check is part of V2 (Formula Citation) and blocks delivery on failure per HC#8.

## Examples

**Example 1: Aggregate calc with handoff.**

User (workbook open with calc_documentation/1 in session): explain Profit Ratio

Skill runs Phase 0 (resolve), Phase 1 (handoff hit), skips Phase 2, composes:

```
**Calc Explanation: Profit Ratio** (Orders)
Signal source: handoff
Author caption: Overall profit margin, aggregate not row-level.

**What it computes.**
Profit Ratio returns the ratio of total profit to total sales, aggregated to whatever grain the worksheet is displaying. Formula: `SUM([Profit]) / SUM([Sales])`. The numerator sums profit across the current row context; the denominator sums sales across the same context.

**Why it is structured this way.**
SUM-of-ratios avoids the average-of-averages pitfall (Pattern: agg-first-then-divide). If the calc were `AVG([Profit] / [Sales])`, each rows ratio would be averaged, which is arithmetically wrong for a portfolio-level margin. The SUM-then-divide pattern respects the underlying dollars.

**How it fits in the calc family.**
Parents (uses): [Profit], [Sales]
Children (used by): Regional Profit YoY, Discount Impact Score, Top 10 Profit Filter
Profit Ratio is a mid-level utility calc; two of its three children are dashboard-facing.

**What to expect at runtime.**
Type: aggregate
Aggregate calcs cannot be placed on Detail; must go on a shelf with a partition context (e.g., Region on Rows). If you try to filter by Profit Ratio directly at the row level, Tableau will refuse and offer to aggregate first. LOD grain matters: this calc respects the shelf-defined grain.

Next: If you need to diagnose why Profit Ratio returns NULL for a specific segment, route to calc-debugger.
```

## Graceful Degradation

These rules apply whenever something this skill needs is missing or fails. More specific rules elsewhere in this file take precedence.

- **Nothing to work on.** If no workbook is open, there is no data source, or the named calc, sheet, dashboard, or data source isn't found, stop before any other step. Say what you found (list the real names, if any) and ask the user to open the workbook or pick one. Never work on a guessed or closest-match target.
- **Tool call fails, times out, or returns empty.** Retry once, then stop retrying. Mark everything that depended on that call as not checked, continue with what you still can, and say which step failed. If the failed call was a write, stop and report the workbook's current state instead of continuing.
- **Partial results.** If any check, sheet, field, or data source wasn't evaluated, the summary says so (Partial: N of M checked; not checked: [list]). Never give a clean, ready, or PASS verdict on a partial run.
- **Reference file won't open.** Use the rules summarized in this file, say [file] unavailable; using the built-in summary, and never make up thresholds, rule IDs, or Desktop menu steps from memory.
- **Peer skill not installed.** If this skill would hand off to another skill that isn't available, say so and give the manual Desktop step instead. A handoff is never the only next step.
- **Platform gap.** If no tool can do something, say so plainly and give the manual Desktop path.
- **Failure messages.** Tell the user in plain language what was done, what wasn't, and the next step. No raw errors, stack traces, or JSON.
- **No fabrication.** Never invent fields, values, findings, or results to fill a gap left by a failed read.
